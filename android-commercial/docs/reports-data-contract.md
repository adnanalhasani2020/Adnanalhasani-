# Reports data contract (Android commercial)

This document defines the source and calculation boundary for the report center. It deliberately distinguishes operational summaries from formal financial statements.

## Date and currency rules
- User-selected dates are inclusive. Timestamped records are filtered from the local zone's start of the start date up to, but excluding, the start of the day after the end date.
- Cloud money fields ending in `_minor` are integer minor units. UI display converts them using the ISO currency's configured fraction digits. Do not sum amounts across different currency codes.
- Local legacy `SaleRecord`, `SettlementRecord`, and `ExpenseRecord` values are displayed as the local app stores them; they are not implicitly converted to cloud minor units.
- Cloud/local sources are not merged.

## Implemented operational reports
- **Completed sales:** `loadCommercialCloudSales` / local `sales_json`; only records whose sale status is `completed` contribute to sales summaries. The gross completed-sales total is not net sales because the return/refund ledger is not subtracted here.
- **Invoice details and line-item sales (cloud):** `loadCommercialCloudSaleDocuments` reads the sale, line snapshots, payment status, discount, tax, and return projections from the organization's existing sales records. The item report uses captured invoice-line quantities and line totals, not current product prices.
- **Sales discounts and recorded taxes (cloud):** uses `discount_minor` and `tax_minor` stored on completed invoices. No rate is inferred. Local reports are unavailable for these measures because the local sale model does not persist these fields.
- **Payments (cloud):** the successful-payment report includes only rows whose payment status is `succeeded`. The status listing can show other statuses but must not be treated as collected cash. It does not add journal entries as a second payment.
- **Collections by payment method:** groups the same successful `commercial_payments` rows by the stored `payment_method_type` and currency. Missing method labels remain a separate "unspecified" group; malformed amount/currency rows block the report. Journal lines are not added to this grouping, so a payment is not double counted.
- **Expenses:** local records come from `expenses_json`; cloud records come from `commercial_expense_vouchers`. Cloud vouchers with a non-empty `canceled_at` are excluded. This is a recorded-expense report, not a complete income statement.
- **Expense summary by category and payment method:** groups non-cancelled cloud expense vouchers by their saved category, payment method and currency. It uses voucher amounts only, rejects invalid amounts/currencies, and does not add the expense journal entry a second time. Missing currency is not defaulted to YER.
- **Purchase invoices:** values come from supplier invoices nested under purchase documents, not from purchase-order totals. Cancelled/void/reversed invoice states are excluded. Outstanding amounts are shown only where a supplier-obligation record exists.
- **Supplier invoice obligations:** grouped by supplier and currency using recorded `amount_due_minor - amount_paid_minor`, floored at zero for display. This is not a full supplier account balance when separate supplier returns or adjustments exist.
- **Supplier invoice price variance:** reads the saved `commercial_supplier_invoice_items` line quantity, invoiced unit price and line total, and joins each line to its originating `commercial_purchase_order_items.unit_cost_minor` baseline. Expected subtotal is `round(sum(quantity × recorded PO unit cost))`, matching the supplier-invoice accrual trigger; variance is saved invoice subtotal minus expected subtotal. Tax and freight are displayed separately and are not included in price variance. The report is withheld if a line/baseline is missing, line totals do not reconcile to the invoice subtotal, or header total does not reconcile to subtotal + tax + freight. This is a purchase price variance report, not a cash/payment report or supplier balance.
- **Returns:** rows expose the return's approval, refund, and restock statuses separately. An approved refund amount is not described as money already refunded; a return request is not automatically counted as a completed stock return.
- **Inventory:** cloud current/available stock and reorder alerts use organization/activity/location-scoped `commercial_inventory_balances`; the available quantity subtracts reserved units. The movement report uses the underlying `commercial_stock_movements` ledger, scoped through the offering's activity and organization. These are not historical valuation reports and do not provide cost/profit.
- **Posted ledger movement:** `loadCommercialCloudPostedJournalLines` joins organization-scoped journal entries with status `posted`, their journal lines, and ledger accounts. Draft/unposted entries are excluded. The trial-balance view aggregates posted debit and credit amounts by account and currency up to the selected end date and exposes the debit/credit difference. It is a review view of the available posted ledger, not a certification that every operational module has been fully mapped.
- **Posted journal details:** shows each posted journal line with account, entry/source reference, debit, credit, and currency. Journal lines are the sole amount source for this report; it does not add the source payment/expense again.

## Ledger-based accounting reports and limits
- **Full customer ledger statement:** the report uses posted journal lines whose `party_account_id` matches the organization-scoped `commercial_customer_party_accounts` mapping. It calculates opening, period movements, running balance, and closing balance by customer and currency. It does not add invoices or payments a second time. It is only available when the party-account mapping and posted-ledger source load successfully; unposted or unmapped customer adjustments cannot appear.
- **Full supplier ledger statement:** uses posted journal lines whose `party_account_id` matches `commercial_supplier_party_accounts`. It separates currencies and shows opening, dated movements, running balance, and closing balance. Operational supplier obligations remain a separate partial report; a return/adjustment is reflected in this statement only when it has been posted to the supplier party account.
- **Income statement and balance sheet:** calculated from posted ledger lines and account types, with each currency reported separately. The report is blocked when the loaded posted entries are unbalanced by entry/currency or account types are unknown. Revenue accounts with debit normal balance or return/discount labels are treated as contra-revenue; COGS is separated from operating expenses when the account is classified/named accordingly. The balance sheet includes cumulative unclosed results in equity and exposes the accounting-equation difference. This is not a certification of missing operational postings.
- **Cash and cash-account movement:** calculates opening balance, detailed period movements, and closing balance from posted lines on mapped cash/bank/clearing accounts, per currency. It is a ledger cash-account movement statement, not a classified operating/investing/financing cash-flow statement. Clearing-account mappings may include unsettled instruments and must be reconciled separately.
- **Historical COGS and gross profit:** uses the sale-line `cost_total_minor` snapshot, never today's purchase price. It subtracts completed return credits and reverses cost only for returned quantities actually restocked. All monetary sums and subtractions use checked integer arithmetic; overflow or missing cost/refund details blocks the report rather than wrapping or substituting zero. Returns in the selected period may refer to sales in an earlier period, so negative period net revenue or net COGS is allowed and is not clamped. It also blocks when a returned tax-bearing invoice cannot be separated into net revenue and tax. It reports gross profit only; it does not claim net profit after operating expenses.
- **Tax and discount detail:** lists stored sales invoice discounts/taxes, supplier invoice tax/freight, and completed return amounts. It does not infer tax rates or claim net tax due after returns when the tax portion of a return is not stored separately.
- **Still not available as authoritative:** historical inventory valuation and inventory-to-GL valuation reconciliation. Current quantity and reorder reports do not become financial valuations merely because a unit-cost field exists; currency, location, and cost-layer reconciliation must be verified first.
- **Customer and supplier aging:** intentionally unavailable until contractual due dates/credit terms and invoice-level remaining-balance allocation semantics are persisted. Invoice creation or obligation recording time is not silently substituted for a due date.
- **Bank reconciliation:** intentionally unavailable until external bank/wallet statement lines, statement identity, matching decisions, and reconciliation state are imported and authorized. A cash/bank GL account movement report is not bank reconciliation.
- **Classified cash-flow statement:** intentionally unavailable until each cash movement can be classified under an approved operating/investing/financing policy. The existing cash/bank report is an account-movement statement only.
- **Statutory tax return:** intentionally unavailable until the business jurisdiction, issuer/tax registration, tax rules and versions, rounding, exemptions, return/credit-note tax allocation, and filing-period rules are configured and reviewed.
- **Historical inventory valuation:** intentionally unavailable until inventory balances, cost layers, receipts, sales, returns, reversals, and warehouse dimensions reconcile over time. Current on-hand × unit-cost is only a current snapshot.
- **Multi-currency consolidation:** intentionally unavailable until an approved rate source, rate timestamp and purpose, translation/rounding method, and realized/unrealized FX policy exist. Currency totals must remain separate meanwhile.
- **User/branch/warehouse performance:** intentionally unavailable where actor and operational dimensions are not reliably stored on every source document; reports must not infer ownership from the current session or branch.

## Exports
- **CSV:** contains the selected report's displayed rows plus report title, inclusive date range, source mode, and export timestamp. It uses UTF-8 with BOM and quoted/escaped cells for spreadsheet compatibility.
- **XLSX:** generated as an Office Open XML ZIP workbook (not renamed CSV), with UTF-8 inline strings, XML escaping, a right-to-left worksheet view, and the same selected rows and report metadata as CSV.
- **PDF export and sharing:** the Android screen writes a paginated PDF through `PdfDocument`, saves it through the Storage Access Framework, and opens the Android share sheet with read permission. It is a basic text layout, not a certified Arabic financial-statement renderer; verify Arabic shaping, pagination, and print appearance on target devices before relying on formal output. A dedicated print-preview action uses Android `PrintManager` and sends the same generated PDF to the system print spooler. Arabic shaping and page layout still require validation on target devices before formal use.
- Exported amounts are the same formatted values shown in the report rows; they are not a substitute for underlying accounting detail or financial-statement certification.


## Financial-report integrity and readiness

The cloud financial reports are read-only projections of organization-scoped posted general-ledger lines. Draft entries are excluded at the repository query. Financial statements fail closed when the ledger cannot be loaded, required GL mappings/control-account roles are missing, dates or currencies are invalid, account types are unknown, or any posted journal is unbalanced by entry and currency. Balances and totals remain separated by currency; the report does not perform implicit FX conversion.

- **Income statement / balance sheet:** income and balance-sheet totals are computed from posted ledger lines through the selected end date. Current-period income is shown separately from unclosed cumulative results and added to equity for the accounting-equation check. A non-zero equation difference is a reconciliation exception, not an automatically repaired value. Revenue/contra-revenue and COGS classifications depend on the chart-of-accounts type, normal balance, and limited legacy account-name/code fallbacks; accounts that cannot be classified are blocked.
- **Cash and bank movement:** opening, running, and closing balances are calculated per mapped cash/bank ledger account and currency from posted journal lines. This is a GL movement statement, not an independently reconciled bank statement. It is withheld when ledger dates or currencies are invalid. A cash transfer is represented by its ledger lines in the affected accounts; review the shared journal/source reference to reconcile both sides.
- **Customer and supplier statements:** full-account views use the mapped accounts-receivable/accounts-payable control accounts, party-account links, matching currency, and posted ledger lines, including opening balances and running balances. The report is withheld if any control-account movement lacks a party link for the same currency. These are GL-side statements; they do not claim operational-to-GL reconciliation unless all operational documents and adjustments are separately matched.
- **Historical gross profit:** uses the cost snapshot saved on the sale line and subtracts the historical cost of returned quantities only when the return was restocked. Sums/subtractions are checked for overflow; missing costs and failed return-cost calculations withhold the report instead of becoming zero. A return in the current period may relate to a prior-period sale, so negative period net revenue or net COGS is valid and remains visible. It is withheld if a tax-inclusive return amount cannot be separated from revenue. It is gross profit, not net profit after operating expenses.
- **Tax and discount detail:** lists only recorded invoice tax/discount fields and approved completed return amounts, with source references and currency. Purchase freight is not reported as tax. Return tax is not represented as net tax when the source does not store a separately attributable tax amount.
- **Current inventory valuation:** uses the recorded unit cost attached to current inventory balances and the mapped inventory-account currency. It is not historical inventory valuation and does not by itself prove agreement to the GL inventory balance.

## Customer collection replay migration

Migration `20261027221500_harden_customer_collection_replay_posting.sql` strengthens idempotent replay: a previously successful customer payment can be replayed only when its posted payment journal entry exists. It returns that posted journal reference and otherwise raises `customer_payment_journal_not_posted`, preventing an apparently successful replay from concealing missing accounting. The migration was applied to the connected Supabase project and the live function definition was queried to confirm the guard is present. It does not by itself reconcile legacy payments or repair historical journals.

Migration `20261027195426_guard_return_adjustment_currency.sql` adds fail-closed checks to both the private collection RPC and the GL posting routine: completed returns must have an approved amount in the sale currency, and refund-posting currencies must match the sale currency. A malformed completed return or cross-currency refund raises an explicit exception instead of being silently omitted from the receivable calculation. The migration was applied to the connected Supabase project and both live function definitions were queried to confirm the guards are present.

## Verification limitations

Source-contract assertions were added for financial-statement gating, party-control ledger statements, historical cost snapshots, and mapped cash accounts. A successful Android Gradle build, APK generation, device-level validation, and full financial reconciliation against populated production transactions must be reported only after those operations actually run. No UI report should be treated as a certified financial statement until the mapped accounts, posted journals, operational sources, and reconciliation exceptions are reviewed.
