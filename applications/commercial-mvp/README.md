# النسخة التجارية الأولى — مسار البيع القابل للاستخدام

**الحالة:** قيد التنفيذ — وثيقة نطاق واختبارات قبول، وليست إعلان جاهزية.  
**الأولوية:** أعلى أولوية منتج حتى ينجح مسار بيع واحد من تسجيل الدخول إلى النتيجة النهائية.

## النتيجة المطلوبة

يستطيع مستخدم حقيقي:
1. تسجيل الدخول بحساب موثّق، مع جلسة قابلة للإبطال وانتهاء صلاحية واضح.
2. رؤية المنتجات/العروض النشطة فقط، مع السعر والعملة والوحدة والموقع/النشاط وسياق المخزون الفعلي.
3. اختيار منتج وكمية صحيحة، ومعرفة الإجمالي قبل التأكيد.
4. تنفيذ البيع مرة واحدة فقط، حتى مع إعادة إرسال الطلب أو انقطاع الاتصال.
5. التأكد من تسجيل البيع وتحديث المخزون بشكل ذري ومتسق، وعدم السماح بمخزون سالب أو بيع يتجاوز المتاح.
6. رؤية إيصال/ملخص نهائي يتضمن رقم البيع وحالته والمنتج والكمية والسعر والإجمالي والرصيد المتبقي.

## ما كشفته مراجعة النواة الحالية

- توجد تطبيقات Python داخلية للمنتجات والعروض والبيع وقراءة المخزون، مع SQLite واختبارات تكامل.
- إنشاء البيع الحالي يتطلب AuthorizationGrant محفوظاً؛ هذا تفويض داخلي وليس تدفق تسجيل دخول للمستخدم النهائي.
- اختبار `test_stage34_commerce_sale_inventory_integration.py` يصرّح صراحة بأن المسار لا يحجز المخزون ولا يخصمه.
- سجلات `InventoryPosition` تمثل ملاحظات/مراكز مخزون مؤرخة؛ لا يجوز تعديلها وكأنها رصيد قابل للخصم من دون سجل حركة مخزون صريح.
- المستودع لا يحتوي حالياً على واجهة Web/Mobile أو API عامة متكاملة؛ النواة وحدها لا تحقق تجربة المستخدم المطلوبة.

لذلك لا يجوز اعتبار إنشاء سجل Sale وحده عملية بيع مكتملة، ولا اعتبار قراءة كمية المخزون حجزاً أو خصماً.

## خطة التنفيذ ذات الأولوية

### P0 — عقد البيع والمخزون (مانع إطلاق)
- إضافة سجل حركة مخزون مستقل وغير قابل للتعديل (مثل بيع/إرجاع/توريد/تسوية مع مرجع مصدر فريد).
- تنفيذ checkout داخل معاملة واحدة: إعادة التحقق من العرض والسعر والسياق والكمية والرصيد، إنشاء البيع وبنوده، تسجيل حركة المخزون، وتسجيل نتيجة العملية.
- قفل/تسلسل الكتابة أو تحديث مشروط بالإصدار لمنع بيع آخر وحدة مرتين تحت التزامن.
- فرض idempotency key فريد مرتبط بالمستخدم وطلب البيع؛ إعادة الطلب نفسه تعيد النتيجة السابقة، واستخدام المفتاح مع حمولة مختلفة يُرفض.
- منع البيع عند الكمية المجهولة أو المتعارضة أو غير الفعالة أو غير الكافية؛ لا تُعامل الحالة المجهولة كصفر ولا تستخدم رصيد نشاط آخر.
- لا يُسمح بالانتقال إلى حالة مكتملة قبل نجاح تحديث المخزون داخل المعاملة نفسها.

### P1 — عرض منتجات قابلة للبيع
- قراءة قائمة من مصدر البيانات الفعلي لا من بيانات تجريبية ثابتة.
- تضمين العرض والمنتج والنشاط الفعالين فقط، واحترام نافذة الصلاحية.
- إظهار الكمية فقط عندما تكون حالة المخزون معروفة وغير ملتبسة، مع إخفاء/تعطيل الشراء عند عدم القدرة على إثبات التوفر.
- إرجاع السعر والعملة والوحدة من مصدر معتمد؛ إذا لم يكن السعر معرفاً فلا يُنشأ سعر افتراضي.

### P2 — الهوية وواجهة الاستخدام
- إضافة تدفق تسجيل دخول حقيقي: اعتماد موثّق، تخزين آمن للأسرار، جلسات محدودة العمر وإبطالها، وحدود لمحاولات الدخول. لا يكفي وجود Person أو AccessAccount أو AuthorizationGrant.
- إنشاء API وواجهة عربية بسيطة: دخول، قائمة منتجات، تفاصيل المنتج، سلة/تأكيد، نتيجة البيع، وسجل عمليات المستخدم.
- تطبيق صلاحيات الخادم على كل طلب؛ لا تُقبل هوية المستخدم أو السعر أو الإجمالي من الواجهة كحقائق موثوقة.

### P3 — الإيصال والمراجعة
- إرجاع نتيجة عملية ثابتة قابلة للاسترجاع بعد انقطاع الاتصال.
- إظهار رقم البيع والحالة والسطور والإجمالي والعملة ووقت العملية والرصيد بعد البيع.
- ربط سجل التدقيق بالفاعل والسياق ومرجع حركة المخزون.

## بوابات القبول الإلزامية

1. **المسار السعيد:** مستخدم موثّق يرى منتجاً نشطاً ذا مخزون معلوم، يشتري كمية متاحة، ثم يرى إيصالاً ويقرأ المخزون الجديد من قاعدة البيانات.
2. **لا بيع فوق المتاح:** شراء كمية أكبر من الرصيد يُرفض ولا يترك Sale أو حركة مخزون جزئية.
3. **لا مخزون مجهول:** الرصيد المفقود/الملتبس لا يسمح بالشراء.
4. **عزل السياق:** مخزون نشاط أو عرض أو موقع آخر لا يزيد الكمية المتاحة لهذا العرض.
5. **التزامن:** طلبان لآخر وحدة لا يمكن أن ينجحا معاً.
6. **إعادة الطلب:** إعادة إرسال طلب ناجح بنفس مفتاح idempotency لا تنشئ بيعاً ثانياً ولا تخصم مرتين.
7. **فشل ذري:** أي فشل بين إنشاء البيع وتسجيل الحركة يعيد كل التغييرات.
8. **السعر:** الإجمالي يحسب في الخادم باستخدام Decimal/وحدات نقدية صحيحة، ويعاد التحقق من السعر وقت التأكيد.
9. **الصلاحية:** العرض/المنتج/النشاط غير النشط أو خارج نافذته لا يمكن شراؤه.
10. **الهوية:** غير المسجل أو الجلسة المنتهية لا يستطيع عرض بيانات خاصة أو تنفيذ بيع.
11. **النتيجة:** يمكن استرجاع إيصال العملية بعد تحديث الصفحة أو انقطاع الاتصال.
12. **اختبارات الانحدار:** تبقى جميع اختبارات النواة الحالية ناجحة.

## تعريف الإنجاز

لا تُعلن النسخة التجارية الأولى جاهزة حتى توجد واجهة قابلة للتشغيل وAPI موثقة ومسار بيع متكامل مع خصم مخزون ذري، وتنجح بوابات القبول السابقة في CI. نجاح اختبارات النواة الحالية وحده لا يحقق هذا التعريف.
