# الكيانات والمفاهيمية — النموذج التفصيلي

## النطاق
هذا نموذج مفاهيمي لا يحدد جداول أو مخطط قاعدة بيانات. المفهوم وحدة معنى مستقلة لها مالك وحالة وعلاقات وزمن وأصل.

**عدد المفاهيم الدومينية الأساسية: 47، إضافة إلى State Record كأداة نمذجة وصفية غير مستقلة.**

## Invariants العابرة للمجالات
1. Person لا يتكرر فقط لتغيير Activity أو Role.
2. Role وFamily Relationship لا يتحولان تلقائياً إلى Authorization.
3. Product وOffering وInventory وAvailability وSale مفاهيم مستقلة.
4. Obligation وDebt وLoan ليست مترادفات.
5. Invoice وPayment وSettlement وLedger Entry ليست مفهوماً واحداً.
6. Balance مشتق ولا يصبح مصدر حقيقة ثانياً.
7. Clinical Record لا يصبح Commercial Record.
8. Recommendation لا تساوي Approval ولا Execution.
9. Provenance لا يساوي Audit.
10. Offline لا يساوي Finality.
11. Device وReplica وPending Operation لا تملك Domain Truth.
12. التصحيح لا يمحو القدرة على تفسير التاريخ.

## ملاحظات خاصة
- Person → Access Account → Authenticator → Session، وبشكل مستقل Person → Financial Account.
- Person ↔ Membership ↔ Activity وMembership ↔ Role Assignment علاقات زمنية.
- Product → Offering → Sale، وOffering ↔ Inventory، وAvailability مشتق زماني/مكاني.
- Sale → Invoice/Obligation → Payment → Settlement → Ledger Entry → Balance، مع بقاء Invoice في Commerce كوثيقة، واعتراف Finance بالأثر المالي.
- Loan ↔ Parties → Obligations/Debt دون افتراض أنه Sale.
- Person → Patient Context → Encounter → Clinical Record → Result/Report/Prescription بالتوازي مع Service → Financial Reference.
- Family Relationship → Delegation → Authorization Grant → Agent Action، مع Approval عند الحاجة.
- Agent → Authority Policy لا يعني ملكية Domain.
- Device → Pending Operation → Submission → Domain Truth، والتعارض يذهب إلى Conflict/Resolution.


## تعميق دفعة 1 — Identity / Activities / Products

### Identity / Access

| المفهوم | المعنى | lifecycle | الزمن | الحقيقة/التغيير |
|---|---|---|---|---|
| Person | الشخص/الجهة التي تستمر هويتها عبر سياقات الوصول والنشاط | created → active/inactive → corrected | identity + recorded/correction | Identity |
| Identifier | معرف/مرجع مرتبط بالشخص وله صلاحية مستقلة | issued → active → replaced/expired/revoked | valid-from/to + recorded | Identity |
| Access Account | سياق وصول للنظام | created → active → suspended → restored/expired/revoked | activation/suspension/revocation | Access |
| Authenticator | وسيلة إثبات حيازة/سيطرة للمصادقة | enrolled → active → lost/revoked/expired → replaced | enrollment/revocation/replacement | Access |
| Session | سياق وصول مؤقت | started → active → terminated/expired | start/end/termination | Access |

Person الواحد قد يرتبط بأكثر من Access Account عندما توجد سياقات وصول مستقلة ذات معنى دلالي/إداري مستقل. الأصل عدم نقل Access Account بين الأشخاص؛ أي استثناء مستقبلي يحتاج واقعة إدارية/قانونية موثقة ولا يعيد تعريف الهوية.

Identity ≠ Authentication ≠ Authorization:
- Identity = من هو الشخص/الجهة.
- Authentication = إثبات الحيازة/السيطرة اللازمة لسياق الوصول.
- Authorization = ما يجوز فعله داخل سياق وغرض ونطاق.
- Identifier ليس Authenticator، وAuthenticator ليس Authorization Grant.

### أحداث وتصحيحات الهوية والوصول

- identity correction: تصحيح Person/Identifier مع حفظ التاريخ اللازم للفهم.
- identifier replacement: إنهاء صلاحية السابق وربط البديل دون محو التاريخ.
- access suspension: تغيير Access Account فقط.
- authenticator revocation: إبطال الوسيلة المتأثرة فقط.
- session termination: إنهاء Session دون تغيير Person أو Financial Account.
- فقد Authenticator لا يساوي فقد Device ولا يغير Identity.

Device لا يصبح Identity؛ الجهاز سياق تشغيل يحمل Sessions/Pending Operations ولا يعرّف الشخص.

### Activities / Memberships / Roles

Activity وOrganization حقائق مستقلة عن Person. Membership تثبت الارتباط بالنشاط، وRole Assignment مسؤولية محددة داخل سياق وفترة.

| المفهوم | lifecycle والزمن |
|---|---|
| Membership | proposed → active → suspended → ended/revoked؛ effective_from/effective_to |
| Role Assignment | assigned → active → suspended/revoked/expired؛ فترة فعالية مستقلة |
| Activity | established → active → suspended/closed |
| Organization | established → active → dissolved |

يمكن تداخل Role Assignments إذا كان ذلك مقصوداً دلالياً. إنهاء العضوية/الدور لا يمحو التاريخ.

Owner ≠ Manager ≠ Employee ≠ Customer. هذه أوصاف سياقية وليست هويات جديدة، ولا تنشئ Authorization أو Financial Account تلقائياً.

Role ≠ Permission ≠ Authorization؛ Role Assignment قد يدخل في تقييم الصلاحية لكنه لا ينشئ Authorization Grant بذاته.

### Products / Services / Offerings

Product تعريف عام يمكن أن يظهر في عدة Activities. Service معنى خدمة دوميني مستقل عندما تكون الخدمة نفسها موضوعاً للهوية/الحالة/الاستخدام. Offering عرض Product أو Service داخل Activity، ويمكن أن يختلف وصفه وشروطه وفترته دون نسخ Product/Service.

Offering lifecycle: draft → published → active → suspended/withdrawn → expired/retired. إيقاف Offering لا يحذف Product/Service ولا يعيد كتابة عروض سابقة.

### Inventory / Availability

Inventory Position تمثل حقيقة كمية/حالة مخزون في سياق مكاني/تشغيلي. لا نضيف Warehouse أو Location كمفهوم دوميني مستقل الآن؛ Location Context كافٍ.

on-hand وreserved معنيان مخزنيان مختلفان، وavailable قيمة مشتقة حالياً من on-hand وreserved والقيود ذات الصلة. adjustment تصحيح معترف به مع أثر تاريخي. لا نضيف Stock Ledger أو Quantity Event في هذه الدفعة.

Availability نتيجة مشتقة من Inventory/Offering/الوقت/الموقع/القواعد، ولها valid-at وfreshness عند الحاجة. قد تصبح stale دون أن تتغير Inventory Truth.

Inventory Truth ≠ Availability Result.


## تعميق الدفعة 2 — المالية والالتزامات والمدفوعات والتسويات

### Financial Account

Financial Account هو **نطاق مالي** له حقيقة مستقلة عن هوية الشخص وعن سياق الوصول. وجود Person مرتبط بالحساب لا يجعل Person هو المالك القانوني في كل ولاية قضائية؛ النموذج يسجل العلاقة المالية والأدوار ذات الصلة دون تقرير ملكية قانونية عامة.

- **Owner of Truth:** Finance.
- **Change Authority:** سلطة مالية مخولة داخل Finance وفق سياق الحساب؛ ليست Access Account.
- **Holder / financial party:** قد يكون Person أو Organization أو طرفاً آخر مسموحاً به؛ لا يُفترض أن يكون هو نفسه صاحب الوصول.
- **Access:** قد يصل أكثر من Access Account إلى بيانات الحساب إذا كانت هناك Authorization مناسبة؛ الوصول لا ينشئ الحساب ولا يملك حقيقته.
- **Currency:** عملة/وحدة نقدية للحساب أو لنطاق الرصيد خاصية دلالية. لا نضيف Currency ككيان جديد في هذه الدفعة. الحساب متعدد العملات لا يفرض مفهوماً مستقلاً ما لم تثبت لاحقاً حاجة مستقلة إلى دورة حياة/ملكية/قيود خاصة بكل رصيد بعملة.
- **Restrictions:** يمكن تقييد الحساب أو تعليقه دون محو التاريخ. restriction/suspension لا يعني إغلاقاً.
- **Closure:** إغلاق الحساب لا يمحو Ledger History ولا يسقط Obligation قائماً. إذا بقيت التزامات أو أرصدة، يسجل الحساب كـclosed مع استمرار القراءة التاريخية؛ ولا يفترض reopening عاماً. إعادة الفتح، إن سمح بها السياق، فعل مستقل يحتاج معنى وسلطة موثقة.
- **Correction:** التصحيح لا يعيد كتابة التاريخ المالي المعترف به ولا يحول Balance إلى حقيقة بديلة.

### Obligation / Debt / Loan

**Obligation** هو المفهوم الأعم: واجب مالي على طرف تجاه طرف/أطراف. قد يكون غير مستحق بعد، مستحقاً، متأخراً، جزئياً، متنازعاً عليه، أو مسدداً. لا يلزم أن يكون له Invoice ولا Payment.

**Debt** ليس كياناً جديداً لمجرد اللغة. هو **تصنيف دلالي أضيق** لـObligation عندما يكون الالتزام مستحقاً بين أطراف في معنى الدين. لذلك لا توجد علاقة مستقلة 1:1 بين Obligation وDebt، ولا lifecycle مستقلة لـDebt.

**Loan** هو علاقة إقراض بشروط؛ يحدد أدوار المقرض/المقترض وشروط الإتاحة والسداد، وقد يولد عدة Obligations (أقساط/فوائد/رسوم بحسب السياق). Loan ليس Debt نفسه، وليس كل Obligation Loan.

القيود:
- الأطراف تُسجل بأدوار دلالية؛ لا يفترض أن النظام نفسه طرف في العلاقة.
- amount، currency، due date، schedule، partial fulfilment، delinquency، dispute، amendment، waiver/cancellation تمثل بحسب ما يلزم لمعنى الالتزام.
- تعديل الشروط لا يمحو الالتزام السابق؛ يجب أن يبقى التاريخ قابلاً للفهم.
- الإعفاء/الإلغاء لا يعني حذف الالتزام من التاريخ؛ بل واقعة/حالة دلالية لها أساس وسياق.

### Invoice

Invoice تبقى **وثيقة Commerce**. الإصدار وحده لا يعني أن أثرها المالي أصبح Ledger Finality، ولا يعني أن المبلغ دُفع.

- Sale قد تنتج Invoice، لكن ليس كل Sale يحتاج Invoice.
- Invoice قد تنشئ أو تشير إلى Obligation.
- Payment قد يخصص إلى Invoice/Obligation وفق السياق.
- Settlement قد يحسم تخصيص القيمة أو يثبت اكتمال التسوية.
- Ledger Entry لا يساوي Invoice ولا ينشأ منها بحكم الاسم وحده.
- amendment/void/correction تحفظ التاريخ ولا تمحو الحالة السابقة من المعنى التاريخي.
- لا نضيف Credit Note/Debit Note/Adjustment/Refund كمفاهيم مستقلة في هذه الدفعة؛ نحتاجها فقط إذا ثبت أن لها مالك حقيقة ودورة حياة وعلاقات لا يمكن تمثيلها داخل Invoice/Obligation/Payment/Settlement.

### Financial Transaction / Payment / Settlement / Transfer

يجب عدم استخدام Financial Transaction كاسم جامع يذيب الفروق:

- **Financial Transaction:** واقعة/حركة مالية مسجلة.
- **Payment:** عملية تقديم قيمة أو محاولة تقديمها لغرض دفع.
- **Transfer:** نقل قيمة بين حسابات/أطراف.
- **Settlement:** حسم/تخصيص/إتمام مالي وفق سياق التسوية.

العلاقات اختيارية وسياقية؛ لا توجد cardinality عالمية تفترض أن كل Payment يساوي Transaction واحداً أو أن كل Settlement ينتج Ledger Entry واحداً.

حالات lifecycle لا تُضاف إلا إذا كان لها معنى مستقل:
- initiated/pending تصف عدم اكتمال المعالجة.
- authorized/accepted تصف تحققاً أو قبولاً في مرحلة معينة، وليست بالضرورة نهائية مالية.
- completed تصف اكتمال العملية وفق معناها، ولا تساوي تلقائياً settled.
- settled تصف اكتمال معنى التسوية.
- failed/rejected/cancelled تصف فشل/رفض/إلغاء قبل الاكتمال وفق السياق.
- reversed تصف أثر عكسي بعد أثر سابق ذي معنى؛ لا تمحو السابق.

### Ledger Entry / Balance

Ledger Entry هو مصدر الحقيقة المالية عندما يصبح الأثر **posted/final وفق قواعد المجال**. ما يزال proposed/pending خارج الحقيقة النهائية للدفتر.

- القيد المعترف به لا يُحذف لإخفاء الخطأ.
- التصحيح يكون عبر أثر تصحيحي/عكسي أو حالة تصحيحية دلالية، بحسب قواعد المجال؛ لا نفرض تقنية.
- reversal لا يعني حذف القيد الأصلي؛ بل يضيف تاريخاً يفسر الانعكاس.
- adjustment/correction يجب أن يترك provenance كافياً لفهم لماذا تغيرت الحقيقة.
- كل Ledger Entry مرتبط بحساب وبسياق مالي، وبمرجع للسبب/العملية عندما يكون ذلك ذا معنى.
- **Balance مشتق:** قراءة لمجموعة قيود وفق account + as-of + currency/scope + قواعد احتساب معلومة.
- Balance قد توجد له قراءات متعددة لنفس الحساب عند as-of مختلف أو عند اختلاف ما إذا كانت الآثار غير النهائية مشمولة؛ لا يجعل ذلك Balance سجلاً مالياً مستقلاً.
- لا تُعامل pending/unposted entries كـLedger Truth. يمكن أن تؤثر في قراءة مشتقة موسومة بوضوح، لكن هذا قرار دلالي للقراءة وليس تغييراً لمصدر الحقيقة.

### الصحة والمال

Health/Service قد ينتج **Financial Reference**، لكن المرجع لا ينقل ملكية Clinical Record إلى Finance ولا يحول الخدمة السريرية إلى Invoice. المسار السريري ومسار الأثر المالي يبقيان منفصلين مع علاقة مرجعية عند الحاجة.

### Family / Delegation

Family Relationship لا تمنح ملكية أو وصولاً مالياً تلقائياً. Delegation/Authorization قد تسمح بالوصول أو الفعل ضمن scope، لكن صاحب الحقيقة المالية يبقى مالك المجال المالي.

### قاعدة قانونية

النموذج لا يحسم من هو «المالك القانوني» للحساب أو الدين أو الأداة في جميع الولايات القضائية. يسجل **financial owner/holder/party role** كمعنى دوميني ويترك الحكم القانوني للسياق والقانون والقرار المستقبلي.

### قاعدة عدم إضافة المفاهيم

لا تُضاف Credit/Debit Adjustment أو Refund أو Chargeback أو Currency Account أو Reconciliation ككيانات مستقلة في هذه الدفعة؛ تُضاف فقط إذا أثبتت مراجعة لاحقة استقلال المعنى والمالك ودورة الحياة والعلاقات.

## تعميق الدفعة 3 — الصحة والسجل السريري والخدمات الصحية

### Patient Context

Patient Context هو **سياق الشخص كمستفيد صحي**. لا ينشئ Person جديداً ولا يعيد تعريف الهوية.

- **Person = الهوية الأساسية.**
- **Patient Context = علاقة/سياق صحي مستمر أو تاريخي للشخص.**
- لا يتحول Patient Context إلى Access Account.
- لا تمنح Family Relationship وصولاً تلقائياً إلى Patient Context.
- Delegation وAuthorization Grant تحددان الوصول أو الفعل فقط عندما توجد سلطة مناسبة.
- **Owner of Truth:** Health.
- **Change Authority:** سلطة صحية مخولة ضمن سياق المجال.
- يمكن للشخص أن يكون له أكثر من Patient Context فقط إذا وجدت سياقات صحية مستقلة ذات معنى فعلي، وليس لمجرد تعدد Encounter أو تعدد الجهات.
- نهاية Patient Context لا تمحو Encounter أو Clinical History السابقة.
- التصحيح يحافظ على التاريخ.
- الحساسية شديدة جداً، ويجب تفسير الوصول وفق purpose وauthorization والسياق القانوني دون وضع سياسة قانونية عالمية هنا.

Patient Context هو مرجع الرعاية، وليس هوية ثانية.

### Encounter

Encounter هو **تفاعل رعاية محدد**.

- قد يبدأه شخص مخول أو جهة/فاعل صحي أو سياق حجز/إحالة بحسب المجال؛ لا نضيف Provider أو Appointment كمفهوم مستقل في هذه الدفعة.
- **Owner of Truth:** Health.
- يمكن أن يحتوي Encounter على عدة Clinical Records.
- قد ينتج أو يرتبط بعدة Results/Reports وPrescriptions حسب سياق الرعاية.
- قد يرتبط بـService وبـActivity/Organization الصحية.
- قد ينتج Financial Reference، لكن الأثر المالي يبقى خارج Health.
- إلغاء Encounter أو انقطاعه لا يمحو السجلات التي نشأت فعلاً قبله.
- completed تعني اكتمال التفاعل وفق معناه، ولا تعني تلقائياً اكتمال كل النتائج أو الوصفات أو التسوية المالية.
- interrupted لا تُستخدم إلا إذا كان الانقطاع حالة لها معنى مستقل، وإلا يكفي تفسير الزمن/الحالة دون توسيع lifecycle.

**Encounter ≠ Invoice ≠ Payment ≠ Financial Account.**

### Clinical Record

Clinical Record ليس حاوية عامة لكل ما له علاقة بالمريض. هو **معلومة سريرية موثقة** تمثل حقيقة أو ملاحظة صحية في سياق محدد.

قد تتضمن المعلومة معنى سريرياً متنوعاً، لكن لا ننشئ Diagnosis أو Allergy أو Lab Test أو Imaging Study أو Medication ككيانات مستقلة الآن.

- **Owner of Truth:** Health.
- **Change Authority:** سلطة سريرية/توثيقية مخولة ضمن المجال.
- يمكن إنشاء السجل من إنسان أو مصدر/جهاز صحي أو نتيجة/عملية موثقة عندما يسمح المجال بذلك؛ المصدر لا يصبح بالضرورة صاحب الحقيقة.
- التعديل لا يمحو الأصل.
- amended تعني وجود تعديل ذي معنى على السجل.
- corrected تعني تصحيحاً لا ينبغي أن يجعل التاريخ السابق غير قابل للفهم.
- invalidated تستخدم فقط عندما تصبح المعلومة غير صالحة للاعتماد وفق معنى صحي مستقل.
- يجب التمييز بين **Current Clinical State** وبين **Clinical History**.
- Provenance يشرح مصدر المعلومة وكيف/بمن تأثرت؛ لا يصبح هو المعلومة السريرية.
- Audit Record يسجل أفعال الوصول/التغيير/الأحداث التي تحتاج تدقيقاً؛ لا يصبح Clinical History.

### Result / Report

Result/Report مفهوم صحي مستقل يمثل **نتيجة أو تقريراً ذا معنى سريري**، وليس مجرد ملف.

يمكن أن يشمل نتائج فحص أو تقرير تصوير أو تقرير خدمة صحية دون إنشاء كيان مستقل لكل نوع.

- **Owner of Truth:** Health.
- يجب معرفة Patient Context عندما يكون الشخص هو موضوع النتيجة، وقد يرتبط Encounter.
- قد يستند إلى Clinical Records أو ينتج/يحدّث معلومات سريرية.
- قد يكون له منشئ/مفسر صحي أو جهة مسؤولة، لكن لا نضيف Provider كمفهوم مستقل الآن.
- preliminary وfinal يميزان مرحلة النتيجة عندما يكون الفرق دلالياً.
- amended وcorrected لا تستبدلان التاريخ بصمت؛ يبقى مسار النسخ/التعديل قابلاً للفهم.
- effective/performed time يصف متى كان المحتوى السريري ذا الصلة؛ issued time يصف متى صدرت النسخة؛ amendment time يصف متى عدلت.
- Provenance وAudit منفصلان عن محتوى النتيجة.

### Prescription

Prescription هو **توجيه/طلب علاجي سريري**، وليس توصية عامة ولا صرفاً للدواء.

الفصل:
- **Clinical Recommendation:** اقتراح/توجيه قد لا يصبح قراراً.
- **Agent Recommendation:** توصية ناتجة عن Agent ولا تصبح حقيقة سريرية لمجرد صدورها.
- **Prescription:** طلب/توجيه علاجي معترف به ضمن السلطة السريرية.
- **Medication Dispensing:** صرف/تسليم فعلي، وهو ليس Prescription نفسه.

لا نضيف Medication/Drug ككيان مستقل الآن؛ يظل موضوع العلاج مرجعاً/وصفاً دلالياً داخل Prescription ما لم تثبت متطلبات لاحقة استقلاله.

Lifecycle المقترح دلالياً:
draft → issued → active → amended → cancelled / expired / fulfilled

لا تُفرض كل الحالات على كل Prescription. fulfilled لا يعني أن الوصفة اختفت؛ بل أن غرضها العلاجي من جهة الوصفة تحقق وفق سياقها. cancelled وexpired لا يمحوان التاريخ.

Prescription قد يرتبط بـEncounter وClinical Record وPatient Context. يمكن أن ترتبط Agent أو Approval بها فقط عبر Authority Policy/Authorization وبقدر ما يسمح به السياق؛ **Agent لا يملك Clinical Truth**.

### Clinical Decision Support وAI

لا نضيف Clinical Decision ككيان مستقل في هذه الدفعة.

المسار المفاهيمي:
Clinical Information → Recommendation → (Approval عند الحاجة) → Agent Action / Human Action

لكن:
- Recommendation ≠ Clinical Decision.
- Agent Recommendation ≠ Prescription.
- Approval لا يعيد تعريف سلطة المجال؛ هو قرار موافقة ضمن سياق محدد.
- Agent Action لا يصبح Clinical Truth بمجرد تنفيذه.
- Agent لا يحصل على سلطة طبية عامة من كونه Agent.
- Authority Policy تحدد ما يمكن فعله، وAuthorization Grant تمنح صلاحية ضمن النطاق، وApproval يستخدم عند الحاجة.
- إذا كان الفعل خارج Authority Policy أو Authorization، فهو محاولة فعل غير مخولة، ولا يصبح حقيقة سريرية.

هذا يتفق مع مبدأ WHO بأن استخدام AI في الصحة يحتاج حوكمة ومسؤولية ومساءلة وحماية للاستقلال البشري، ولا ينبغي أن ينقل القرارات الطبية التي يجب أن تبقى تحت سيطرة البشر إلى الآلة. هذا **دليل مفاهيمي** وليس قراراً قانونياً للمشروع.

### Health ↔ Finance

المسار المفاهيمي الممكن:

Patient Context → Encounter → Service → Financial Reference → Invoice / Obligation / Payment

لكن:
- Service مجانية: قد لا يوجد Financial Reference فعلي.
- Service مدفوعة: قد يوجد Financial Reference وأثر مالي مستقل.
- الدفع الجزئي أو الالتزام المالي يبقى في Finance.
- إلغاء الخدمة لا يعيد تفسير Clinical Record؛ الأثر المالي إن وجد يعالجه Finance.
- Clinical Record لا يصبح Finance.
- Prescription لا يصبح Invoice.
- Encounter لا يصبح Financial Account.
- Financial Reference هو رابط فقط ولا ينقل ملكية الحقيقة السريرية إلى Finance.

لا نضيف مفاهيم مالية جديدة في هذه الدفعة.

### Family / Delegation / Children

Family Relationship ≠ Authorization.

Parent/guardian relationship لا تعني تلقائياً أن أحد الطرفين يستطيع رؤية أو تعديل Patient Context أو Clinical Record. صلاحية الوصول تعتمد على Delegation/Authorization والسياق العمري/القانوني عندما يكون ذلك ذا صلة.

- Delegation قد تكون مؤقتة ومحدودة النطاق.
- سحب Delegation لا يمحو ما كان مصرحاً به تاريخياً.
- Authorization Grant قد يحدد target/scope/action.
- Agent قد يعمل تحت Delegation، لكنه لا يكتسب ملكية Clinical Truth.
- النموذج لا يحسم قوانين الولاية القضائية الخاصة بالأطفال أو الولي أو سن الرشد.

### Privacy / Sensitivity

جميع المفاهيم الصحية الأساسية هنا حساسة جداً.

يجب فصل:
- **Data Classification:** وصف حساسية البيانات.
- **Authorization:** من يجوز له فعل ماذا ضمن scope.
- **Purpose:** لماذا يستخدم الوصول/المعلومة.
- **Audit:** ما الفعل الذي يجب تتبعه لأغراض الرقابة.
- **Retention:** معنى الاحتفاظ ومدته عندما يحدده المجال أو القانون.

لا تتحول هذه الدفعة إلى تصميم صلاحيات أو تشفير أو سياسة احتفاظ قانونية عالمية.

### الزمن الصحي

يجب التفريق عند الحاجة بين:
- clinical/effective time: متى كانت المعلومة أو الحالة صحيحة سريرياً.
- encounter time: متى حدث تفاعل الرعاية.
- performed/effective time: متى حدثت الواقعة التي تتعلق بها النتيجة.
- issued time: متى صدرت النتيجة/الوصفة.
- recorded time: متى سُجلت المعلومة.
- amendment/correction time: متى حدث التعديل أو التصحيح.
- cancellation/expiry time: متى انتهت صلاحية الفعل الصحي.

النسخة الحالية من المعلومة لا تلغي القدرة على فهم النسخ السابقة.

### قاعدة عدم إضافة المفاهيم

لا نضيف في هذه الدفعة:
Diagnosis، Clinical Decision، Provider، Appointment، Medication، Drug، Allergy، Lab Test، Imaging Study، Specimen، Care Plan أو أي مفهوم صحي فرعي آخر.

السبب: لم يثبت في المتطلبات الحالية أن أيّاً منها يحتاج الآن مالك حقيقة ودورة حياة وعلاقات مستقلة لا يمكن تمثيلها بالمفاهيم الحالية. يمكن أن تبقى هذه المعاني كتصنيفات/مراجع دلالية داخل Clinical Record/Result/Report/Prescription إلى أن تثبت حاجة مستقلة.

### الحدود الأساسية

Person ≠ Patient Context ≠ Access Account

Clinical Record ≠ Provenance ≠ Audit Record

Recommendation ≠ Approval ≠ Prescription

Prescription ≠ Dispensing

Encounter ≠ Invoice ≠ Payment

Financial Reference ≠ Clinical Record

Agent ≠ Clinical Truth

## تعميق الدفعة 4 — الأسرة والتفويض والاتصال والوكلاء

### Family Relationship

Family Relationship تمثل علاقة أسرية/قرابة أو سياقاً أسرياً بين أشخاص، وقد تشمل علاقة ذات دلالة على الرعاية أو المسؤولية بحسب السياق، دون أن تتحول بذاتها إلى هوية أو دور أو صلاحية وصول.

- **المعنى المستقل:** حقيقة العلاقة الأسرية نفسها.
- **مالك الحقيقة:** Family domain/context المختص.
- **Change Authority:** جهة مخولة بإثبات/تعديل العلاقة ضمن السياق؛ لا يفترض نموذج قانوني عالمي.
- **الزمن:** العلاقة قابلة للتغير؛ effective-from/to أو حالات الانتهاء/النزاع تستخدم عندما يكون لها معنى.
- **التاريخ:** انتهاء العلاقة أو تصحيحها لا يمحو أن لها وجوداً تاريخياً.
- **القاصر/الطفل:** يمثل الشخص نفسه مع سياق العلاقة؛ لا ينشئ النموذج تلقائياً قاعدة وصول أو وصاية قانونية.
- **الحدود:** Family Relationship ≠ Authorization ≠ Delegation ≠ Access Account ≠ Role ≠ Permission.

### Delegation

Delegation تمثل نقل/إسناد مسؤولية أو قدرة على التصرف في نطاق محدد، وقد تستند إلى Family Relationship أو Membership أو سياق آخر، لكنها لا تتطلب وجود علاقة أسرية في كل حالة.

- لها نطاق وهدف وفترة وشروط ومصدر تفويض وحالة.
- يمكن أن تكون proposed/active/suspended/revoked/expired عندما تكون الحالات ذات معنى مستقل.
- لا تستخدم Delegation كمرادف لـPermission.
- لا تجعلها مصدر حقيقة المجال الذي يتصرف فيه المفوض له.
- يمكن أن يكون منحها أو سحبها مقيداً بسياق السلطة؛ التفاصيل القانونية تبقى jurisdiction-dependent.

### Authorization Grant

Authorization Grant تمثل منحاً محدداً للسلطة:

**Subject + Target/Context + Action + Scope + Purpose + Validity + Conditions + Grant Basis + Status**

الحالات لا تضاف لمجرد الشيوع؛ يستخدم proposed/pending/granted/denied/revoked/expired فقط حيث تميز حالات ذات معنى مستقل.

- **Grantor:** من يملك سلطة المنح في السياق.
- **Revocation:** من يملك سلطة السحب وفق أساس المنح.
- **Consumers:** قرار السماح بفعل محدد، لا Domain Truth.
- **Boundary:** Authorization Grant ≠ Family Relationship ≠ Role Assignment ≠ Authority Policy ≠ Approval.

### Conversation

Conversation هي سياق تواصل مستقل يجمع مشاركين ورسائل ضمن نطاق وزمن وحالة.

- المشاركون قد يكونون Person/Agent/Activity/Organization أو أطرافاً أخرى بحسب السياق.
- لا تُنشأ أنواع منفصلة للمحادثات بحسب المجال ما لم يظهر فرق دلالي مستقل.
- الحالة مثل opened/active/closed/archived تستخدم فقط عندما يكون لها معنى.
- مالك تغيير حالة المحادثة هو صاحب السلطة على سياق الاتصال، وليس بالضرورة أحد المشاركين.
- Conversation لا تصبح Clinical Record أو Financial Transaction لأنها تتناول موضوعاً صحياً أو مالياً.

### Message

Message هي وحدة تواصل ذات معنى، وليست مجرد ملف أو نص خام.

تحمل مفاهيمياً:
- sender / sender context
- content/meaning
- composed time
- sent time إن اختلف
- delivery/read status عند الحاجة
- correction/amendment أو withdrawal/deletion فقط عندما يكون لها معنى مستقل
- provenance عند الحاجة

Message قد ترتبط بـDomain Reference، لكن الإشارة إلى حقيقة صحية أو مالية لا تنقل ملكية الحقيقة إلى Communication.

### Agent

Agent هو فاعل/قدرة تشغيلية يمكن أن تكون بشرية أو برمجية أو جهة ممثلة في سياق العمل.

- لا يساوي Person ولا User.
- لا يملك Domain Truth.
- لا يصبح Authorization لمجرد كونه Agent.
- دورة الحياة تستخدم registered/active/suspended/retired فقط إذا كانت كل حالة ذات أثر مستقل.
- فقد أو تعطيل Agent لا يمحو تاريخ المجال الذي سبق أن أثّر فيه.

### Authority Policy

Authority Policy تمثل القاعدة الدلالية التي تحدد حدود أفعال Agent:

- الفاعل/الوكيل المعني
- نطاق الهدف
- أنواع الأفعال
- الشروط
- الفترة
- الحاجة إلى Approval
- أساس انتهاء/سحب السلطة

Authority Policy ليست Role ولا Permission ولا Authorization Grant، ولا تحدد تنفيذاً تقنياً.

### Agent Action

Agent Action يمثل فعلاً أو محاولة فعل قام بها Agent أو نُسبت إليه في سياق السلطة.

يجب التفريق مفاهيمياً بين:
- Observation: معلومة/ملاحظة دخلت في السياق.
- Recommendation: اقتراح لما قد ينبغي فعله.
- Preparation: إعداد فعل لم ينفذ.
- Approval: قرار بالموافقة أو الرفض على فعل يحتاج قراراً.
- Execution: وقوع الفعل في المجال.
- Agent Action: سجل/تمثيل الفعل أو المحاولة المنسوبة إلى Agent، مع outcome وسياق authority.

Agent Action لا يصبح Domain Truth. إذا أثّر على Finance/Health/Activity، فالحقيقة النهائية تعود إلى Owner Domain.

### Approval

Approval مفهوم مستقل لقرار بشأن فعل/طلب محدد يحتاج موافقة.

يحمل مفاهيمياً:
- requested action
- requester
- approver/decision authority
- requested_at
- decided_at
- decision/status
- rejection reason عند الحاجة
- cancellation/withdrawal عند الحاجة
- العلاقة بالفعل الذي ستتبعه الموافقة

Approval ≠ Authorization Grant:
- Authorization Grant يحدد ما يمكن منحه/السماح به ضمن نطاق وشروط.
- Approval يقرر بشأن فعل محدد.
- ليس كل Agent Action يحتاج Approval؛ ذلك تحدده Authority Policy وطبيعة الفعل.
- Approval لا ينقل ملكية Source of Truth.

### الصحة والمال

Health:
Clinical Information → Recommendation → Approval عند اللزوم → Human/Agent Action → Health Source of Truth.

- Recommendation ≠ Prescription.
- Recommendation ≠ Clinical Decision.
- Agent Action ≠ Clinical Truth.
- Agent لا يصبح صاحب Clinical Record أو Prescription لمجرد تنفيذ فعل.

Finance:
Agent → Authority Policy → Agent Action → Approval عند الحاجة → Financial Domain Truth.

- Agent لا يملك Financial Account أو Ledger Entry أو Balance.
- Agent Action لا يثبت Settlement أو Financial Finality بذاته.
- Approval لا ينقل ملكية Financial Truth.

### التاريخ والتصحيح

Provenance ≠ Audit Record ≠ Domain Truth.

يجب أن يبقى قابلاً للتفسير:
- من أنشأ/غيّر Family Relationship.
- من منح/سحب Delegation أو Authorization Grant.
- من أنشأ/أرسل/صحح Message.
- من طلب/وافق/نفذ Agent Action.
- مصدر السلطة والقرار.

التصحيح لا يعني محو التاريخ المفاهيمي، وAudit Record لا يصبح مالكاً لأي Domain Truth.
