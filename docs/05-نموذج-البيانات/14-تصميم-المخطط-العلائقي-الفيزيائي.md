# Physical Relational Schema Design

**Baseline:** `main @ 4f6916a724a412dad3528977be2cca95b3599b76`  
**Scope:** Documentation / physical schema design only.  
**Status:** Proposed relational design; no database, SQL DDL, migration, ORM/repository implementation, `src/`, `tests/`, or `schema/` changes are authorized.

## 1. Purpose and boundary

This document translates the approved Logical Data Model / Persistence Architecture into a relational schema design suitable for a later migration implementation.

It defines:

- proposed relational tables and relationships;
- primary and foreign keys;
- nullability and lifecycle/state fields;
- uniqueness and integrity constraints;
- provenance/audit references;
- indexes;
- logical transaction boundaries;
- optimistic concurrency controls;
- GAP-0005 idempotency constraints;
- GAP-0006 identity uniqueness and merge constraints;
- GAP-0001 / GAP-0003 AgentAction, Approval, and AuthorizationGrant constraints;
- Stage 12A financial constraints;
- historical/audit retention semantics;
- schema/model versioning and migration strategy.

It does **not**:

- create a physical database;
- create SQL DDL;
- create migrations;
- change `src/`, `tests/`, or physical `schema/`;
- start persistence implementation;
- start Stage 12B;
- change `v1.0.0`, tags, or releases.

The design preserves the Owner Domain rule: a relational foreign key/reference does not transfer domain ownership.

## 2. Relational conventions

### 2.1 Identifier convention

Every authoritative table has an immutable surrogate primary key named `<entity>_id`, represented later by a repository-approved UUID/identifier type.

Natural identifiers may be additionally unique, but are not used as the sole relational identity unless the governing specification explicitly requires it.

### 2.2 Common columns

Unless a table-specific section says otherwise, authoritative tables carry:

- `id` / entity identifier;
- `created_at` NOT NULL;
- `updated_at` NOT NULL;
- `created_by_ref` NULLABLE where system-generated records are possible;
- `provenance_id` NULLABLE/NOT NULL according to source requirements;
- `version_no` NOT NULL for mutable entities requiring optimistic concurrency.

The exact physical type, clock precision, and timezone storage are implementation choices for migration design; timestamps are logically UTC-normalized.

### 2.3 Foreign-key policy

Foreign keys are used for relationships owned within the same persistence boundary and for stable cross-boundary references where referential enforcement is compatible with lifecycle rules.

Where historical retention, asynchronous domain acceptance, or cross-domain ownership prevents a physical FK, the reference remains a typed logical reference and is validated at the domain boundary.

No database-level cascade may silently erase financial, authorization, audit, provenance, or historical truth.

### 2.4 State transitions

Lifecycle/state fields are NOT NULL when state governs operation eligibility.

State changes are optimistic-concurrency protected and must be auditable. Reversal/correction creates historical evidence instead of silently overwriting the prior semantic event.

## 3. Proposed relational tables

The following table set is the baseline proposed physical schema. Derived read models are explicitly separated in §5.

### 3.1 Identity and access

#### 1. `persons`
- **PK:** `person_id`
- **Required:** `person_id`, `state`, `created_at`, `updated_at`, `version_no`
- **Nullable:** profile/metadata fields as allowed by specification; `provenance_id` nullable only for trusted system bootstrap.
- **State:** active/suspended/merged/deactivated.
- **FKs:** `canonical_person_id` → `persons.person_id` for merged identity history; self-reference must not form cycles.
- **Unique:** none on raw profile attributes.
- **Indexes:** `canonical_person_id`, state.

#### 2. `identifiers`
- **PK:** `identifier_id`
- **Required:** `person_id`, `identifier_type`, `normalized_value`, `uniqueness_scope`, `state`, timestamps.
- **FK:** `person_id` → `persons.person_id`.
- **Unique:** composite normalized identity key including `identifier_type` and declared uniqueness scope.
- **Indexes:** person lookup; normalized identity lookup; state/scope.
- **GAP-0006:** uniqueness applies to canonical active identity claims; historical claims remain queryable.

#### 3. `access_accounts`
- **PK:** `access_account_id`
- **Required:** `person_id`, `state`, timestamps, `version_no`.
- **FK:** `person_id` → `persons.person_id`.
- **Unique:** account identity according to access specification.
- **Indexes:** person/state.

#### 4. `authenticators`
- **PK:** `authenticator_id`
- **Required:** `access_account_id`, `authenticator_type`, `state`, `enrolled_at`, timestamps.
- **FK:** `access_account_id` → `access_accounts.access_account_id`.
- **Nullable:** revocation timestamp/reason.
- **Unique:** provider/type-specific external identity where applicable.
- **Indexes:** account/state.

#### 5. `sessions`
- **PK:** `session_id`
- **Required:** `access_account_id`, `device_id`, `state`, `started_at`, timestamps.
- **FKs:** access account; device.
- **Nullable:** `ended_at`, termination reason.
- **Indexes:** account/state; device/state; active-session lookup.

#### 6. `devices`
- **PK:** `device_id`
- **Required:** `device_fingerprint_ref`, `state`, timestamps.
- **Nullable:** current account/person association.
- **Unique:** stable device identity within its declared scope.
- **Indexes:** account/person association; state.

- **Nullable:** descriptive fields as permitted.
- **State:** active/suspended/ended.
- **Indexes:** owner/state; effective lifecycle.

#### 8. `memberships`

- **FKs:** person; activity.
- **Unique:** at most one active membership for the same person/activity under the applicable membership semantics.

#### 9. `role_assignments`

#### 10. `products`
- **PK:** `product_id`
- **Required:** `product_id`, `state`, timestamps, `version_no`.
- **Nullable:** descriptive/catalog attributes.
- **Unique:** product identity where an external canonical key exists.
- **Indexes:** state; owner/catalog context.

#### 11. `services`

- **Nullable:** service description/category.

#### 12. `offerings`

- **Nullable:** `effective_to`, service reference when the offering represents a service.
- **FKs:** product; activity; optional service.

- **FKs:** activity; optional product/offering references only where they are authoritative context links.
- **Unique:** one current position per declared inventory scope/key.

#### 14. `sales`

- **Unique:** externally supplied sale key if specified.

#### 15. `invoices`
- **PK:** `invoice_id`

- **Unique:** invoice number within issuer scope.
- **Indexes:** sale/state; issuer/number; obligation.

#### 17. `obligations`

- **Required:** creditor/debtor party refs, amount/currency representation, `state`, timestamps, `version_no`.
- **Nullable:** source invoice, due date, loan reference.
- **FKs:** invoice/loan only where lifecycle supports physical enforcement; parties are typed identity refs.
- **Unique:** no duplicate business obligation key when supplied by an upstream authority.
- **Indexes:** party/state/due date; invoice; loan.

#### 18. `loans`

#### 19. `payments`

- **FK:** obligation only where one-to-one/one-to-many allocation semantics are explicitly supported; otherwise typed allocation reference.
- **Unique:** provider payment identity within provider scope; governed operation identity where applicable.
- **Indexes:** obligation/state; provider identity; operation identity.

#### 20. `settlements`
- **PK:** `settlement_id`

- **FKs:** payment; obligation.

#### 21. `financial_transactions`
- **PK:** `financial_transaction_id`
- **Required:** `settlement_id` or authorized Finance recognition source, amount/currency, `state`, recognition timestamp, timestamps.
- **FK:** settlement.
- **Unique:** one final recognition identity per authoritative settlement/effect.
- **Indexes:** settlement; recognition time; account references.

#### 22. `ledger_entries`

- **FKs:** financial account; financial transaction.
- **Unique:** immutable recognition/effect identity plus entry sequence as required.
- **Indexes:** account + posted_at + entry_sequence; transaction.
- **Stage 12A:** only Finance recognition may create final ledger truth.

## 4. Relationship summary

The principal relational paths are:

- Person → Identifier / Access Account / Membership.
- Activity → Membership / Role Assignment / Offering / Sale.
- Product → Offering.
- Service → Offering.
- Offering → Inventory Position context / Sale.
- Sale → Invoice.
- Invoice → Obligation where the commercial flow creates one.
- Obligation ← Settlement ← Payment.
- Settlement → Financial Transaction → Ledger Entry → Financial Account.
- Instrument → Instrument Usage.
- Family Relationship → Delegation → Authorization Grant.
- Agent → Agent Action → Authorization Grant.
- Agent Action → Approval.
- Conversation → Participant / Message.
- Patient Context → Encounter / Clinical Record / Result/Report / Prescription.
- Device → Pending Operation.
- Durable Operation Record → outcome/domain reference.
- Audit/Provenance/Domain History reference any authoritative target without acquiring its ownership.
- Workflow → Workflow Event.

Derived concepts are not promoted to authoritative tables:

- **Availability** derives from Offering + Inventory Position + context + freshness.
- **Balance** derives from authoritative Ledger Entries.
- **Debt** is a classification of Obligation.
- authorization/approval applicability remains a derived evaluation.

A later read-model table for Availability or Balance may be introduced only as explicitly non-authoritative and must carry source/version/as-of semantics.

## 5. Nullability and derived-data policy

### Required vs nullable

A field is NOT NULL when absence would make the row semantically invalid, untraceable, or unable to participate in its governing lifecycle.

A field is nullable when:

- the lifecycle legitimately introduces it later;
- the relationship is optional by specification;
- the record can be system-generated without a human actor;
- the domain explicitly allows anonymous/guest context.

Nullable does not mean “unknown authority.” Missing required authority/ownership references are rejected at the domain boundary.

### Derived data

Persisted derived values must include enough source/version/as-of information to be reproducible.

No derived table may be used to satisfy:

- GAP-0002 authority resolution;
- final financial recognition;
- authorization source-of-truth checks;
- final inventory truth.

## 6. Index design

The minimum index families are:

### Identity
- normalized identity uniqueness: `identifier_type + uniqueness_scope + normalized_value`;
- person canonical target;
- identifier → person.

### Activities
- activity owner/state;
- membership `person_id + activity_id + state`;
- role assignment `membership_id + role_code + effective interval`.

### Commerce
- product state/catalog context;
- offering `product_id + activity_id + state + effective interval`;
- service state/category;
- inventory `offering/product + location + state + freshness`;
- sale `activity_id + occurred_at + state`;
- invoice issuer/number and sale/state.

### Finance
- obligation party/state/due date;
- payment obligation/state;
- settlement payment;
- settlement obligation;
- financial transaction settlement/recognition time;
- ledger account + posted_at + entry sequence.

### Authorization
- grant subject/action/context/state/effective interval;
- delegation subject/context/effective interval;
- agent action grant binding and state/time;
- approval action/state;
- policy key/version/effective interval.

### Recovery/integrity
- pending operation device/state/queued time;
- pending operation namespace/operation identity;
- durable operation `namespace + operation_id`;
- conflict target/domain/state.

### Evidence/history
- audit target + occurred_at;
- audit actor + occurred_at;
- provenance target/source;
- domain history target + historical timestamp;
- workflow namespace/id;
- workflow + event sequence.

Indexes must serve authoritative lookup and lifecycle queries first. Broad text/search indexes are outside this design unless a later specification requires them.

## 7. Transaction boundaries

These are logical transaction boundaries to be implemented later; this document does not prescribe database transaction syntax.

### 7.1 Single-domain atomic operations

The following must be atomic within their Owner Domain:

1. Product definition mutation.
2. Offering state/effective-period mutation.
3. Inventory Position mutation plus its governing operation identity.
4. Sale state transition plus required authoritative references.
5. Authorization Grant lifecycle transition.
6. AgentAction binding/state transition.
7. Approval transition.
8. Payment local state transition.
9. Settlement local state transition.
10. Finance recognition creating the Financial Transaction/Ledger effect.
11. Durable Operation Record creation/finalization for the governed operation.

### 7.2 Cross-domain operations

Cross-domain workflows must not require a single global database transaction.

The protocol is:

1. create/resolve durable operation identity;
2. resolve all authoritative references;
3. perform the Owner Domain operation;
4. record the accepted authoritative reference/outcome;
5. publish/consume the next domain step using durable identity;
6. make retry/replay deterministic.

A failure in a downstream domain must not silently rewrite the upstream domain's authoritative truth.

### 7.3 Financial boundary

Stage 12A remains controlling:

**Payment → Settlement → Financial Transaction → Ledger Entry → Balance (derived).**

Only the Finance recognition path creates final ledger truth.

### 7.4 Offline boundary

Offline state ends at Pending Operation / Conflict.

Offline execution cannot commit final:

- Inventory Position;
- Payment;
- Settlement;
- Financial Transaction;
- Ledger Entry.

## 8. Optimistic concurrency

Mutable authoritative rows use a monotonic `version_no` or equivalent revision token.

Required pattern:

- read row + version;
- calculate allowed transition;
- write only if the expected version still matches;
- increment version atomically;
- reject stale writes deterministically.

High-contention tables that require this include:

- offerings;
- inventory_positions;
- sales;
- obligations;
- payments;
- settlements;
- authorization_grants;
- agent_actions;
- approvals;
- pending_operations;
- durable_operation_records.

Append-oriented evidence/history tables do not need mutable-row locking for their semantic history; they require unique event/effect identities instead.

Optimistic concurrency must never be used to manufacture a second financial effect after a retry. Stage 12A idempotency/effect identity remains authoritative.

## 9. GAP-0005 idempotency constraints

The relational design requires a durable operation uniqueness boundary:

**Unique key:** `(namespace, operation_id)`.

For each record:

- `request_fingerprint` is canonicalized before comparison;
- same key + same fingerprint returns the prior deterministic outcome;
- same key + different identity-defining fingerprint becomes CONFLICT;
- an existing record cannot be replaced by the conflicting request;
- final outcome/result reference is stable after finalization;
- the record survives process/runtime restart.

Where Pending Operation and Durable Operation Record both exist, they represent different concerns:

- Pending Operation = offline/recovery queue state.
- Durable Operation Record = global operation identity/replay authority.

They must not create competing operation identities.

---

## 10. GAP-0006 identity uniqueness and merge constraints

The physical design must enforce:

1. normalized identity value participates in the uniqueness key;
2. identifier type participates in the key;
3. declared uniqueness scope participates in the key;
4. only canonical/eligible identity claims participate in current uniqueness;
5. merged identities retain historical references;
6. canonical target chains terminate;
7. merge cycles are rejected;
8. a non-canonical merged identity cannot be silently reintroduced as a new canonical identity;
9. historical identifiers remain resolvable to the canonical identity;
10. identity merge operations are themselves durable, auditable, and idempotent.

The exact normalization algorithm is owned by GAP-0006 and should not be reimplemented independently in the database layer.

## 11. Authorization and approval constraints

### 11.1 Grant → AgentAction

For `agent_actions.authorization_grant_id`:

- nullable only until the governed action is bound;
- once bound, immutable;
- at most one authoritative Grant per AgentAction under the existing Option A semantics;
- Grant subject/action/scope/context must match the AgentAction at enforcement;
- revoked/expired Grant cannot authorize a new execution;
- historical Grant remains resolvable for past actions.

### 11.2 Approval → AgentAction

For `approvals.agent_action_id`:

- exact target action is mandatory;
- an approval for another action cannot satisfy execution;
- only `APPROVED` satisfies the current execution gate;
- PENDING/REJECTED remain explicit states;
- approval history is retained;
- if multiple approval gates are later introduced, each gate gets a distinct deterministic identity rather than overwriting the prior approval.

### 11.3 Delegation and role boundaries

- Family Relationship does not imply Delegation.
- Delegation does not imply unrestricted Authorization.
- Role Assignment does not equal Authorization Grant.
- Activity ownership does not imply unrestricted authority over individual data.
- Guardian/family authority remains contextual and cannot be inferred solely from relationship existence.

## 12. Stage 12A financial constraints

The physical design must preserve these non-negotiable separations:

| Entity | Role | May create final ledger truth? |
|---|---|---|
| Payment | payment operation/state | No |
| Settlement | payment-to-obligation settlement state | No |
| Financial Transaction | recognized financial effect | Only through Finance recognition |
| Ledger Entry | final financial ledger truth | Only Finance recognition |
| Balance | derived view | No |

Additional constraints:

- Settlement references exactly one Obligation.
- Settlement is linked to its Payment according to the accepted matching semantics.
- Duplicate recognition of the same authoritative effect is rejected/idempotently replayed.
- Balance has no independent write authority.
- WorkflowId is unique within its workflow namespace and grants no authority.
- Reversal/correction creates traceable historical evidence.
- Financial state is not finalized while offline.
- No Invoice, Sale, Payment, or derived Balance row may masquerade as Ledger truth.

Financial amounts must be represented with a migration-safe exact numeric/currency model chosen by the later implementation; floating-point storage is not acceptable for authoritative monetary values.

## 13. Historical and audit retention semantics

### 13.1 Authoritative current state

Current-state tables may update lifecycle/state fields, but updates must remain traceable.

### 13.2 Audit records

Audit records are append-oriented evidence.

Retention must be long enough to satisfy the applicable governance, security, operational, and legal requirements. Exact retention periods are Specification/jurisdiction dependent and are not invented here.

### 13.3 Provenance

Provenance records must remain available for as long as the derived/authoritative value needs to be explained or reconstructed under applicable policy.

### 13.4 Domain history

Financial, authorization, identity-merge, and other high-impact corrections/reversals must preserve historical evidence.

### 13.5 Deletion

Physical deletion is not permitted merely because a record is no longer current when doing so would destroy:

- financial truth/history;
- authorization evidence;
- identity-merge history;
- audit evidence;
- provenance required for reconstruction;
- contractual/historical state required by specification.

Where privacy/legal deletion later requires removal, it must be implemented as an explicitly governed retention/deletion policy with evidence that distinguishes data minimization from destruction of mandatory historical truth.

## 14. Migration and schema-versioning strategy

No migration is created by this PR.

### 14.1 Version layers

Maintain separate identifiers for:

1. logical model version;
2. physical schema version;
3. application release/tag.

A schema version must map to an approved logical model revision. It must not be equated with `v1.0.0`.

### 14.2 Expand → migrate → validate → contract

For compatible evolution:

1. expand schema with additive structures;
2. deploy compatible readers/writers when needed;
3. backfill using explicit provenance;
4. validate counts, uniqueness, references, lifecycle invariants, and historical continuity;
5. switch authoritative reads/writes;
6. contract obsolete structures only after validation and retention review.

### 14.3 Constraint rollout

For existing data:

- validate before adding strict uniqueness/FK constraints;
- repair/reconcile through explicit domain operations;
- record backfill/reconciliation provenance;
- never hide violations by destructive deletion.

### 14.4 Dual-read / dual-write

Dual-read or dual-write is allowed only when:

- the migration requires it;
- the window is explicit and time-bounded;
- source-of-truth ownership is explicit;
- reconciliation is deterministic;
- rollback behavior is documented.

It is not a default architecture.

### 14.5 Rollback

Schema rollback and domain-state rollback are separate.

A failed migration may roll back schema mechanics where safe, but must not silently roll back:

- financial recognition;
- authorization evidence;
- audit/provenance history;
- identity merge history.

Compensating domain operations are required when semantic state must be corrected.
