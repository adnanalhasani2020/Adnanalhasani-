## 1. Family Relationship

Family Relationship تمثل حقيقة العلاقة الأسرية/القرابة أو السياق الأسري بين الأشخاص.

### حدودها

- Family Relationship ≠ Authorization.
- Family Relationship ≠ Delegation.
- Family Relationship ≠ Access Account.
- Family Relationship ≠ Role.
- Family Relationship ≠ Permission.

العلاقة قد تكون زمنية، قابلة للانتهاء أو التغيير أو النزاع، ويجب الحفاظ على تاريخها المفاهيمي عند التصحيح.

### القاصر والوصاية

الطفل/القاصر يبقى Person في النموذج، ويمكن أن يرتبط بعلاقات أسرية مستقلة. لا يقرر النموذج قاعدة عالمية بأن الوالد أو القريب يحصل تلقائياً على الوصول.

**Parent → Automatic Access غير معتمد.**

أي أثر قانوني للوصاية أو التمثيل يعتمد على DEC-0001 والاختصاص القانوني والسياق، ولا يحول Family Relationship إلى Authorization بذاتها.

## 2. Delegation و Authorization Grant

### التمييز

| المفهوم | المعنى |
|---|---|
| Relationship | حقيقة علاقة بين أطراف |
| Delegation | إسناد/نقل مسؤولية أو قدرة على التصرف في نطاق محدد |
| Role | صفة/دور داخل سياق |
| Permission | وصف دلالي لفعل مسموح به، وليس بالضرورة منحة مستقلة |
| Authorization Grant | منحة سلطة محددة بشروط ونطاق ومدة |
| Authority Policy | قاعدة تحدد حدود السلطة وما يتطلبه الفعل |

لا توجد سلسلة إلزامية:

**Family Relationship → Delegation → Authorization**

قد توجد Delegation بلا Family Relationship، وقد يوجد Authorization Grant بلا Delegation أسرية.

### Authorization Grant

يجب أن تكون قابلة للتفسير عبر:

**Subject + Target/Context + Action + Scope + Purpose + Validity + Conditions + Grant Basis + Status**

الحالات تستخدم فقط عندما يكون لها معنى مستقل. يمكن أن تظهر proposed/pending/granted/denied/revoked/expired حسب السياق، دون فرضها جميعاً كقائمة ثابتة.

### السلطة

- من يمنح؟ جهة/طرف يملك سلطة المنح في السياق.
- من يلغي؟ الجهة التي تملك سلطة السحب وفق أساس المنح.
- من يستهلك؟ تقييم الفعل/السماح وليس مصدر حقيقة المجال.

Authorization لا تصبح مصدر حقيقة للأسرة أو الصحة أو المالية أو النشاط.

## 3. Conversation و Message

### Conversation

Conversation هي سياق تواصل مستقل يحدد المشاركين والنطاق والزمن والحالة عند الحاجة.

لا تنشأ أنواع منفصلة لمحادثة مستخدم↔مستخدم، عميل↔موظف، مريض↔جهة صحية، مستخدم↔Agent لمجرد اختلاف المشاركين.

### Message

Message هي وحدة تواصل ذات معنى، وليست ملفاً أو نصاً خاماً.

يجب أن يمكن تفسير:
- المرسل وسياقه.
- معنى/محتوى الرسالة.
- وقت الإنشاء.
- وقت الإرسال إذا اختلف.
- حالة التسليم/القراءة عند الحاجة.
- التصحيح/التعديل.
- الإلغاء/الحذف إذا كان له معنى مستقل.
- Provenance عند الحاجة.

### الحدود

**Communication ≠ Clinical Truth.**

**Communication ≠ Financial Truth.**

يمكن أن تحتوي الرسالة على إشارة إلى Patient Context أو Invoice أو Obligation أو عملية، لكن الإشارة لا تنقل Source of Truth إلى Message.

## 4. Agent

Agent فاعل/قدرة تشغيلية يمكن أن تكون بشرية أو برمجية أو جهة ممثلة في سياق العمل.

يحافظ النموذج على:

- Agent ≠ Person.
- Agent ≠ User.
- Agent ≠ Domain Owner.
- Agent ≠ Source of Truth.
- Agent ≠ Authorization.

دورة الحياة لا تُثبت إلا بقدر ما يلزم: registered/active/suspended/retired يمكن استخدامها عندما تملك الحالات معنى مستقلاً.

تعطيل أو تقاعد Agent لا يمحو تاريخ الأفعال أو الحقائق الدومينية السابقة.

---

## 5. Authority Policy

Authority Policy تمثل حدود السلطة مفاهيمياً:

- من/ما الذي يمكن للAgent فعله.
- نطاق الهدف.
- نوع الفعل.
- الشروط.
- الفترة.
- هل يتطلب الفعل Approval.
- متى تنتهي/تسحب السلطة.

ليست:
- API scopes.
- OAuth scopes.
- database permissions.
- RBAC implementation.
- policy engine.

هذه الدفعة لا تختار أي تنفيذ تقني للصلاحيات.

---

## 6. Agent Action

يجب فصل:

**Observation → Recommendation → Preparation → Approval → Execution**

مع بقاء Agent Action تمثيلاً للفعل أو محاولة الفعل المنسوبة إلى Agent في سياق السلطة.

### الحدود

- Recommendation ≠ Approval.
- Approval ≠ Execution.
- Agent Action ≠ Domain Truth.

الفعل خارج Authority Policy أو Authorization لا يصبح صحيحاً لمجرد حدوث محاولة؛ يسجل كسياق فعل/محاولة وتعود الحقيقة النهائية إلى Owner Domain.

### الصحة

Clinical Information → Recommendation → Approval عند اللزوم → Human/Agent Action → Health Source of Truth.

- Recommendation ≠ Prescription.
- Recommendation ≠ Clinical Decision.
- Agent لا يصبح صاحب Clinical Record أو Prescription.

### المال

Agent → Authority Policy → Agent Action → Approval عند الحاجة → Financial Domain Truth.

Agent لا يصبح:
- Financial Account owner.
- Ledger owner.
- Balance source.
- Settlement authority تلقائياً.

---

## 7. Approval

Approval كيان مستقل لقرار بشأن فعل محدد يحتاج موافقة.

يحمل مفاهيمياً:
- requester.
- requested action.
- decision authority.
- requested_at.
- decided_at.
- approver.
- decision/status.
- rejection reason عند الحاجة.
- cancellation/withdrawal عند الحاجة.
- reference إلى الفعل الذي ستتبعه الموافقة.

**Approval ≠ Authorization Grant.**

Authorization يحدد السلطة الممكنة ضمن نطاق وشروط.

Approval يقرر بشأن فعل محدد.

ولا يُفترض أن كل Agent Action يحتاج Approval؛ ذلك تحدده Authority Policy وطبيعة الفعل.

---

## 8. Provenance و Audit

**Provenance ≠ Audit Record ≠ Domain Truth.**

يجب أن يبقى قابلاً للتفسير:
- من أنشأ/غيّر Family Relationship.
- من منح/سحب Delegation أو Authorization Grant.
- من أنشأ/أرسل/صحح Message.
- من طلب Agent Action.
- من وافق.
- من نفذ.
- ما أساس السلطة أو القرار.

Audit Record يوثق ما يلزم للتدقيق، وProvenance يصف الأصل/السياق/الاشتقاق، ولا يملك أي منهما الحقيقة الدومينية.

## 9. الحدود مع Batch 2 وBatch 3

### Health

- Patient Context يبقى مملوكاً لـHealth.
- Clinical Record يبقى الحقيقة السريرية.
- Prescription تبقى حقيقة صحية.
- Agent Action وRecommendation لا ينقلان الملكية إلى Agent.
- Approval لا يصبح Clinical Truth.

### Finance

- Financial Account وLedger Entry وBalance تبقى ضمن ملكية Finance كما اعتمدت في Batch 2.
- Agent Action لا يصبح Ledger Truth.
- Approval لا يثبت Settlement وحده.
- Authorization لا يصبح Financial Account أو Financial Truth.

### Activity / Organization / Membership

- Membership وRole Assignment لا تمنح Authorization تلقائياً.
- Agent لا يصبح Activity Owner لمجرد الفعل.
- Owner/Manager/Employee/Customer لا تتحول تلقائياً إلى Authorization.

### Access Account / Device

- Access Account ≠ Domain Truth.
- Device ≠ Domain Truth.
- فقد Device لا يمحو Family/Authorization/Conversation/Agent history.

## 10. Offline / Pending / Conflict

**Offline Operation ≠ Domain Finality.**

خصوصاً:
- Delegation.
- Authorization Grant.
- Approval.
- Agent Action.
- Sensitive Message.

Pending Operation يمكن أن تمثل محاولة محلية، لكنها لا تثبت القرار أو الفعل النهائي.

Conflict لا ينشئ Source of Truth ثالثاً.

Message queued لا تعني delivered.

Approval محلي لا يصبح قراراً نهائياً لمجرد وجوده على Device.

Agent Action محلي لا يثبت وقوع الأثر في المجال.

لا يتضمن هذا النموذج أي Sync Algorithm أو CRDT أو آلية تقنية.
