# Data Model / Persistence Architecture Definition

**Baseline:** `main @ 093e04c0e5c9e4520c210bb93eb392703468a05e`  
**Scope:** Documentation / Architecture / Data Model only.  
**Status:** Proposed architecture definition; no schema, migration, repository implementation, or database creation is authorized by this document.

## 1. Purpose and boundary

This document translates the existing Requirements, Decisions, Stage 5 conceptual model, Stage 6 Specifications, Stage 11 integrity contracts, and the closed Stage 12A design/implementation boundaries into a persistence-oriented logical model.

It is intentionally **pre-schema**:

- no SQL tables are created;
- no ORM/repository classes are introduced;
- no migrations are written;
- no `src/`, `tests/`, `schema/`, or persistence implementation is changed;
- Stage 12B remains **NOT AUTHORIZED / NOT STARTED**;
- `v1.0.0`, tags, and releases are unchanged.

The primary scope is **Commerce + Daily Services** under DEC-0010, while preserving the already-established Identity, Authorization, Finance, Offline/Recovery, Audit, and Provenance boundaries.

### Normative ownership rule

Each domain entity has one **Owner Domain** that remains its authoritative source of truth. References, caches, discovery results, audit records, provenance records, and orchestration state do not acquire ownership merely by storing a reference to the entity.

This follows the existing GAP-0002 Semantic Integrity Contract and Stage 12 Source-of-Truth Matrix.

## 3. Entity contract: common fields

All authoritative persistent entities should be modeled conceptually with a common identity/lifecycle discipline, without prescribing physical column names yet.

### 3.1 Identity

Every persistent entity has:

- stable immutable entity identifier;
- entity type/domain identity where cross-domain references require it;
- creation provenance;
- lifecycle timestamps appropriate to the entity;
- optional version/revision marker where optimistic concurrency or historical reconstruction requires it.

Identifiers are not semantic authority by themselves. GAP-0002 requires resolution against the Owner Domain.

### 3.2 Ownership

Every authoritative entity has an explicit Owner Domain.

Ownership is distinct from:

- access;
- processing authority;
- delegation;
- approval;
- business role;
- legal ownership claims not modeled by the system.

For REQ-FUNC-0010 / DEC-0017, Activity ownership never implies unrestricted authority over individual data.

### 3.3 Lifecycle and state

State is explicit when it affects whether an operation may proceed.

Examples:

- Activity: active/suspended/ended as applicable.
- Offering: draft/active/ended/withdrawn as applicable.
- Inventory Position: observed/effective/closed according to inventory semantics.
- Sale: lifecycle states defined by Commerce specification.
- Payment: lifecycle/finality state.
- Settlement: pending/matched/settled/reversed as applicable.
- Authorization Grant: active/suspended/revoked/expired where defined.
- Agent Action: proposed/prepared/delegated-execution/approved/executed/rejected as applicable.
- Approval: PENDING/APPROVED/REJECTED under existing GAP-0001 semantics.
- Pending Operation: queued/submitted/finalized/rejected/conflicted/cancelled as applicable.
- Conflict: detected/resolved/rejected as applicable.

State transitions must be append-traceable; correction/reversal does not erase historical truth.

## 4. Commerce + Daily Services model

DEC-0010 establishes Commerce + Daily Services as the strategic first priority.

### 4.1 Product

**Identity:** immutable Product ID.  
**Ownership:** Commerce/Product domain.  
**Relationships:** Product ↔ Offering; Product may be referenced by Inventory Position.  
**Lifecycle:** definition lifecycle independent of each Offering.  
**Audit/Provenance:** creation, correction, retirement, source references.  
**Idempotency:** creation/update operations use durable operation identity where governed.  
**Authorization:** activity/user action requires applicable role/authorization.

**Constraint:** Product is not an Offering and does not own Sale/Inventory.

### 4.2 Offering

**Identity:** immutable Offering ID.  
**Ownership:** Commerce/activity context.  
**Relationships:** Product → Offering; Offering → Activity; Offering → Inventory Position; Offering → Sale.  
**Lifecycle:** effective interval plus commercial state.  
**State:** draft/active/ended/withdrawn as specified.  
**Audit/Provenance:** source Product, Activity, creator/action, amendments.  
**Authorization:** changes require authority within the Activity context.

**Constraint:** an Offering is not a copy of Product and does not become inventory truth.

### 4.3 Service

**Identity:** stable Service ID.  
**Ownership:** Daily Services/Commerce domain.  
**Relationships:** Service may be offered through Offering and may be referenced by an Encounter where an existing domain requires it.  
**Lifecycle:** active/effective/retired as specified.  
**Audit/Provenance:** definition and amendments.  
**Authorization:** service-management actions remain activity/context constrained.

No new appointment/scheduling entity is introduced here; scheduling semantics remain Specification-dependent until an existing requirement requires them.

### 4.4 Inventory Position

**Identity:** stable Inventory Position ID, scoped to its owner/activity/location semantics.  
**Ownership:** Inventory domain.  
**Relationships:** Offering/Product context; Availability derives from it.  
**Lifecycle:** observed/effective/closed with freshness.  
**State:** quantity/position state according to the existing inventory specification.  
**Audit/Provenance:** source observation, correction, reconciliation.  
**Idempotency:** inventory-affecting operations require durable operation identity when governed.  
**Authorization:** inventory mutation is activity/role constrained.

DEC-0012 requires that no final inventory save occurs without internet connectivity. Offline state may exist as Pending Operation but does not become final Inventory Truth.

### 4.5 Availability

Availability is **derived**, not a competing inventory source.

It is calculated from:

- Offering;
- Inventory Position;
- location/context;
- relevant activity/service constraints;
- freshness/observed time.

DEC-0009 makes Available Nearby dependent on Offering/Inventory/Availability/location/freshness.

Persisted availability snapshots, if later justified, must carry source/version/as-of metadata and remain non-authoritative.

### 4.6 Sale

**Identity:** immutable Sale ID.  
**Ownership:** Commerce.  
**Relationships:** Offering → Sale; Sale → Buyer context; Sale may reference Invoice/Payment/Obligation.  
**Lifecycle:** initiated/confirmed/completed/cancelled/returned etc. only as defined by Specification.  
**Audit/Provenance:** actor, activity, channel context, referenced Offering, amendments.  
**Authorization:** Activity/Role/Authorization Grant governs mutation; high-impact actions may require Approval.

DEC-0008 means channels are contexts for the same commerce operations, not separate commerce domains.

### 4.7 Invoice / Obligation / Payment / Settlement

These remain separate entities:

**Invoice**
- commercial claim/document;
- may reference Sale;
- may create/reference an Obligation depending on context;
- does not become Financial Ledger truth.

**Obligation**
- Financial Relations source of truth;
- parties and terms are durable;
- Debt is a classification of due Obligation, not a separate competing entity.

**Payment**
- payment operation/state;
- may allocate against an Obligation;
- Payment ≠ Settlement.

**Settlement**
- settlement/matching state;
- may reference Payment and Obligation;
- Settlement ≠ Financial Transaction ≠ Ledger Entry.

Stage 12A already establishes the canonical financial chain:

**Payment → Settlement → Financial Transaction → Ledger Entry → Balance (derived)**

with exact Payment/Settlement and Settlement/Obligation matching, ONE Settlement → ONE Obligation, and Finance-only final recognition.

## 5. Identity / Authorization / Approval model

### Person / Identifier

- Person is identity truth.
- Identifier is a durable identity claim within an explicit uniqueness scope.
- GAP-0006 requires deterministic normalization/uniqueness and canonical identity resolution.
- Historical references resolve to canonical identity without deleting history.

### Access Account / Authenticator / Session / Device

These form the access boundary, not domain ownership.

- Access Account controls access context.
- Authenticator controls enrollment/revocation.
- Session records access lifecycle.
- Device records device identity/lifecycle.
- Device never becomes owner of domain truth.

### Membership / Role Assignment

- Membership links Person ↔ Activity.
- Role Assignment links a Membership/context to role authority over an effective interval.
- Role does not itself equal authorization.

### Authorization Grant / Delegation

- Delegation represents a bounded delegation relationship.
- Authorization Grant is the authorization source of truth.
- Grant references subject/action/scope/context as defined by the applicable specification.
- REQ-FUNC-0005/0006/0028 require family/guardian authority to remain contextual, not blanket authority.
- DEC-0017 requires individual rights and legal/contextual constraints to prevail over activity authority.

### Agent / Authority Policy / Agent Action / Approval

- Agent has configured identity/context.
- Authority Policy is versioned and time-bounded.
- Agent Action has stable identity and lifecycle.
- Authorization Grant is the authorization source.
- Approval is a separate per-action gate under GAP-0001.
- DEC-0014 makes autonomy risk-tiered.
- DEC-0015 makes Human Approval risk/action-class based.
- Exact Grant → AgentAction binding from GAP-0003 remains authoritative.

## 6. Audit, provenance, history

### Audit Record

Audit records are durable evidence of actions/access/events.

They do not own domain truth.

Required conceptual attributes:

- audit record ID;
- event type;
- actor/agent/context;
- target reference;
- timestamp;
- result/status;
- correlation/operation reference where applicable;
- provenance reference where required.

### Provenance

Provenance answers **where a value/state/decision came from**.

It must reference an authoritative source or authoritative historical record.

A provenance record cannot create authority merely by existing.

### Domain History

Domain History preserves amendments, corrections, reversals, and historical references.

Rule:

> correction/reversal changes current state according to domain rules but never silently erases the historical record.

## 7. Idempotency and durable operation integrity

GAP-0005 establishes a distinct **Durable Operation Authority**.

A durable operation record conceptually contains:

- operation_id;
- namespace;
- operation_kind;
- actor/context;
- canonical request_fingerprint;
- status;
- outcome/result reference;
- timestamps;
- relevant provenance/correlation references.

### Uniqueness

**Operation key = operation_id within its governed namespace.**

Same key + same fingerprint:

- no second semantic effect;
- deterministic replay of the stored outcome.

Same key + different identity-defining semantics/fingerprint:

- deterministic CONFLICT;
- previous record is never replaced.

The operation record is not domain truth. It only owns operation identity/replay integrity.

## 8. Authorization / approval references

Persistence must preserve references needed to prove why a governed action was permitted:

- AgentAction → exact AuthorizationGrant;
- AgentAction → applicable Approval when required;
- Approval → exact AgentAction;
- Grant → subject/action/scope/context;
- Delegation → Authorization Grant(s);
- Role Assignment → Grant evaluation context;
- domain action → Activity/actor context where relevant.

References must remain historically resolvable after authority changes.

Revocation/expiry affects new execution according to the governing lifecycle; it must not rewrite historical evidence.

## 10. Persistence boundaries

### Boundary A — Identity / Access

Owns:

Person, Identifier, Access Account, Authenticator, Session, Device.

Does not own:

Financial Account, Sale, Ledger Entry, Authorization truth.

### Boundary B — Activities / Commerce / Daily Services

Owns:

Activity, Membership, Role Assignment, Product, Offering, Service, Sale.

References:

Identity and Authorization.

Does not own:

individual identity truth or financial ledger truth.

### Boundary C — Inventory / Discovery

Owns:

Inventory Position.

Produces:

Availability/Discovery derived views.

Does not own:

Product or Offering definitions.

### Boundary D — Authorization / Agents / Approval

Owns:

Delegation, Authorization Grant, Agent, Authority Policy, Agent Action, Approval.

Does not own:

domain resources merely because it authorizes access to them.

### Boundary E — Financial Relations / Payments / Finance

Financial Relations owns:

Obligation, Loan.

Payments/Settlement owns:

Payment, Settlement.

Finance owns:

Financial Account, Financial Transaction, Ledger Entry.

Balance is derived from Finance Ledger.

### Boundary F — Communication

Owns:

Conversation, Participant, Message.

Domain Reference points outward and never transfers ownership.

### Boundary G — Health

Owns:

Patient Context, Encounter, Clinical Record, Result/Report, Prescription.

Financial references are cross-domain references only.

### Boundary H — Offline / Recovery / Operation Integrity

Owns:

Device-local Pending Operation, Conflict, Durable Operation Record.

It does not own final domain truth.

### Boundary I — Audit / Provenance / History

Owns:

Audit Record and cross-domain evidence structures.

It does not replace any Owner Domain.

## 11. Logical transaction boundaries

This is a **logical** transaction definition, not a DB transaction prescription.

### Local atomic boundaries

Within an Owner Domain, a state change and the domain invariants required to accept it should be committed as one logical atomic unit.

Examples:

- Sale state + its own mandatory references;
- Inventory Position mutation + operation identity;
- Authorization Grant state transition;
- Approval state transition;
- AgentAction state transition;
- Payment/Settlement local state transition;
- Ledger recognition within Finance.

### Cross-domain boundary

Do not require one global transaction to make unrelated domains share ownership.

Cross-domain workflows use:

1. durable operation identity;
2. authoritative reference resolution;
3. domain-local acceptance;
4. explicit cross-domain references;
5. deterministic failure/replay semantics.

For financial recognition, Stage 12A remains normative: only Finance Recognition Command may create final Ledger truth.

### Offline boundary

Pending Operation is a separate persistence boundary from final domain state.

Offline persistence cannot create:

- final Payment;
- final Settlement;
- final Financial Transaction;
- final Ledger Entry;
- final Inventory save.

DEC-0011 and DEC-0012 remain controlling.

## 12. Constraints and indexes

The following are **logical constraints/index requirements**, not SQL definitions.

### Identity / GAP-0006

- normalized identity uniqueness key must be unique within its declared identity scope;
- identity type participates in uniqueness;
- canonical identity target must be deterministic;
- merged/non-canonical targets must not become new canonical identities;
- historical references must resolve deterministically;
- merge cycles are prohibited.

### GAP-0002 Semantic Integrity

- every governed reference resolves against its Owner Domain;
- unknown authoritative entity = rejection;
- owner-domain mismatch = rejection;
- payload claims cannot override authoritative ownership;
- derived/cache/audit records cannot satisfy authority lookup.

### GAP-0005 Durable Operation Integrity

- unique `(namespace, operation_id)`;
- same key with different fingerprint = conflict;
- same key with same fingerprint = idempotent replay;
- operation kind is identity-defining where specified;
- operation record survives runtime restart.

### GAP-0003 Authorization binding

- AgentAction has at most one authoritative AuthorizationGrant binding under the existing Option A implementation semantics;
- binding is immutable once established;
- referenced Grant must remain historically resolvable;
- Grant subject/action must match AgentAction at enforcement.

### GAP-0001 Approval

- Approval must reference the exact AgentAction it approves;
- an approval for another action cannot satisfy the gate;
- only APPROVED satisfies the current execution gate;
- Approval lifecycle remains the existing PENDING/APPROVED/REJECTED model unless a later decision changes it.

### Stage 12A / financial constraints

- Payment ≠ Settlement ≠ Financial Transaction ≠ Ledger Entry;
- Settlement matches exactly one Obligation under Stage 12A;
- one Settlement → one Obligation;
- Finance recognition is the only final Ledger creation path;
- Balance has no independent write authority;
- WorkflowId is unique within its applicable workflow namespace;
- WorkflowId does not grant authority;
- offline cannot create financial finality;
- reversal/correction preserves history;
- duplicate recognition cannot create a second final effect.

### Commerce

- Product ID unique;
- Offering ID unique;
- Offering must reference a valid Product and Activity context where required;
- Inventory Position cannot be used as Offering truth;
- Sale references an authoritative Offering;
- cross-domain references are resolved before governed semantic effect;
- historical Sale/Invoice/Obligation references remain resolvable.

### Authorization/privacy — DEC-0017/0018

- Activity ownership does not grant unrestricted individual-data authority;
- access/processing authority must be evaluated separately from ownership;
- purpose/context/sector/jurisdiction are explicit evaluation dimensions where applicable;
- guardian authority is contextual and cannot be inferred from family relationship alone;
- access, modification, delegation, and execution are separate capabilities;
- no universal legal age is encoded by the data model.

### Suggested logical indexes

At minimum, later schema work should evaluate indexes for:

- entity primary IDs;
- normalized identity uniqueness;
- Owner Domain + entity ID;
- Activity + effective interval;
- Person + Activity Membership;
- Offering + Activity + effective state;
- Offering + Inventory Position scope;
- Sale + Activity + occurred time;
- Obligation + party + status;
- Payment + Obligation;
- Settlement + Payment;
- Settlement + Obligation;
- Financial Account + Ledger Entry time/order;
- AgentAction + AuthorizationGrant;
- Approval + AgentAction;
- Delegation + subject/context/effective interval;
- Authorization Grant + subject/action/context/effective interval;
- Device + Pending Operation state;
- Pending Operation + operation identity;
- Conflict + target/domain/status;
- Audit target + event time;
- Provenance target + source;
- Durable Operation namespace + operation_id;
- WorkflowId + workflow namespace.

Uniqueness and foreign-key behavior must be finalized during schema design; this document intentionally does not choose SQL syntax or physical index names.

## 13. Migration and versioning strategy

No migration is created by this PR.

The later schema strategy should use:

1. **Model version** — version the logical data model independently from application release/tag.
2. **Schema version** — every physical schema revision maps to an approved logical model revision.
3. **Expand → migrate/backfill → validate → contract** for incompatible changes where feasible.
4. **No destructive deletion of historical truth** merely to simplify a new schema.
5. **Explicit provenance** for backfilled/derived values.
6. **Dual-read/dual-write only when explicitly justified and time-bounded**; do not introduce it automatically.
7. **Rollback plan** must distinguish schema rollback from domain-state rollback; historical financial/authorization/audit truth is not silently rolled back.
8. **Versioned reference semantics** where a change could make old references ambiguous.
9. **Constraint-first rollout**: establish data invariants and validation before tightening uniqueness/foreign-key constraints on existing data.
10. **No v1.0.0 coupling**: schema version is not a release/tag decision.
