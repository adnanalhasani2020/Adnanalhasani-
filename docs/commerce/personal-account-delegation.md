# الحسابات الشخصية والتفويض للحسابات الفرعية

## الهدف

يملك المستخدم حساب منصة شخصيًا مستقلًا عن أي مؤسسة. ينشأ له رقم حساب فريد من commercial_create_personal_account. يمكن ربط المؤسسات التي أنشأها أو يملكها بحسابه الشخصي، وتظهر أنشطة كل مؤسسة تحته. كما يستطيع طلب ربط حساب شخص آخر برقم حسابه داخل مؤسسة محددة. الربط التلقائي يعمل عند إنشاء الحساب الشخصي أو المؤسسة؛ ويمكن ربط المؤسسات الموجودة يدويًا من شاشة الحسابات الشخصية.

## المصادقة

- شاشة إعداد النشاط تستخدم Supabase Auth بالبريد الإلكتروني وكلمة المرور؛ لا تستخدم تسجيل الدخول عبر Google.
- عند التسجيل يختار المستخدم اسم عرض، ويحفظ كـ Auth user metadata.
- كلمة المرور لا تحفظ في جداول التجارة ولا ترسل إلى مخزن SQLite.
- إنشاء الحساب الشخصي ورقم الحساب خطوة منفصلة بعد المصادقة، ويجب ألا تُعرض بيانات شخصية حساسة عند البحث برقم الحساب.

## دورة التفويض

1. الحساب الرئيسي يدخل رقم الحساب الشخصي للابن/المستخدم الفرعي.
2. تعرض المنصة رقم الحساب والاسم الظاهر فقط، ولا تكشف البريد أو الهاتف أو وثائق الهوية.
3. يحدد الحساب الرئيسي المؤسسة، الصلاحيات (view_reports, book, purchase)، تاريخ الانتهاء الاختياري وسقف الإنفاق.
4. ينشئ النظام طلبًا بحالة pending_merchant_approval ويرسل إشعارًا إلى مديري المؤسسة.
5. يراجع مالك/مدير/مسؤول المؤسسة الطلب، ويحدد الاسم والأيقونة اللذين يظهر بهما الحساب الفرعي داخل المؤسسة، ثم يقبله أو يرفضه.
6. لا يصبح التفويض فعالًا إلا بعد موافقة المؤسسة. عند تعديل الصلاحيات أو السقف يعود التفويض لانتظار الموافقة من جديد.
7. يستطيع الحساب الرئيسي إلغاء التفويض. تُرفض العمليات الجديدة بعد الإلغاء أو الانتهاء.

## قواعد الشراء والحجز

- الشراء والحجز يمران عبر RPCs مخصصة تتحقق من auth.uid()، وملكية الحساب الفرعي، والمؤسسة، والصلاحية، ونطاق النشاط، والانتهاء، والعملة، وسقف الإنفاق.
- يحتفظ الطلب والحجز بمعرّف التفويض، والحساب الرئيسي صاحب الالتزام المالي، والحساب الفرعي المنفذ.
- الفاتورة/الطلب يرتبط بحساب العميل الخاص بالحساب الرئيسي داخل المؤسسة؛ لا ينشأ التزام مالي باسم الحساب الفرعي.
- يُقفل سجل التفويض داخل معاملة الشراء ويحدّث الإنفاق المتراكم داخل المعاملة نفسها؛ إعادة الطلب بنفس مفتاح idempotency لا تحتسب الإنفاق مرتين.
- يمنع الخادم الطلب إذا تجاوز المبلغ السقف أو اختلفت العملة عن عملة المؤسسة المستخدمة لسقف الإنفاق. يُعاد تحرير المبلغ المحجوز عند إلغاء/رفض الطلب أو الحجز، وتبقى بيانات العملية محفوظة للتدقيق.
- تقارير الإنفاق تعرض طلبات الشراء والحجوزات المسجلة تحت التفويض المطابق للحساب الرئيسي والحساب الفرعي. لا يملك الحساب الفرعي قراءة هذا التقرير إلا بصلاحية view_reports، ويستطيع الحساب الرئيسي ومديرو المؤسسة المخولون مراجعته. هذه الصلاحية لا تمنح تلقائيًا حق الوصول إلى جميع تقارير المؤسسة التشغيلية؛ ذلك يحتاج سياسة تفويض منفصلة لكل تقرير.

## التقارير والإشعارات

- يستطيع الحساب الرئيسي فتح ملخص موحد لجميع الحسابات الفرعية حسب المؤسسة والحساب، مع إجمالي المشتريات والحجوزات والإنفاق المحتسب، ثم فتح تفاصيل العملية وبنودها لكل تفويض.
- عند اعتماد التفويض أو رفضه أو تعديل صلاحياته، تُسجل إشعارات داخل صندوق الإشعارات في التطبيق، ويمكن تعليمها كمقروءة. هذه إشعارات داخل التطبيق وليست إشعارات نظام الهاتف/Push حتى الآن.
- صلاحية `view_reports` تتيح تقرير إنفاق ومشتريات وحجوزات التفويض فقط؛ لا تمنح الوصول تلقائيًا إلى تقارير المخزون أو الأرباح أو التقارير المالية الداخلية للمؤسسة. يلزم تصميم صلاحيات مستقلة لهذه التقارير قبل فتحها للحسابات الفرعية.

## حدود التنفيذ الحالية

- قائمة المؤسسات في شاشة الحسابات الفرعية تعرض المؤسسات النشطة المنشورة في دليل المنصة؛ المؤسسات غير المنشورة تحتاج مسار اكتشاف/ربط إداري منفصل.
- عند موافقة التاجر، يربط النظام الحساب الرئيسي بسجل العميل الموجود فقط إذا تطابق البريد المؤكد بصورة فريدة داخل المؤسسة. إذا لم يوجد سجل مطابق، ينشئ حساب عميل وذممًا مستقلين داخل المؤسسة باسم الحساب الرئيسي ويربطهما به؛ ولا ينشئ أي التزام مالي على الحساب الفرعي. إذا كان البريد يطابق أكثر من سجل، تُرفض الموافقة لمنع إسناد الدين إلى عميل خاطئ.
- هذا التغيير يضيف مسارات RPC وواجهة Android، لكنه لا يُعد منشورًا على Supabase الإنتاجي حتى تُراجع الترحيلات وتُطبق وتُختبر على بيئة مطابقة. وجود الملفات في GitHub وحده لا يثبت أن الخادم الحي يستخدمها.
- لا تُفعّل صلاحيات إضافية بمجرد إظهار زر في الواجهة؛ التحقق في الخادم هو المرجع النهائي.
