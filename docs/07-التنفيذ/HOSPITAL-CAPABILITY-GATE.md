# بوابة اعتماد قدرات المستشفى — جرد وحدود التشغيل

**الحالة:** وثيقة ضبط نطاق ومراجعة؛ لا تمنح اعتمادًا سريريًا أو ماليًا جديدًا.  
**آخر مراجعة:** 2026-10-17  
**مرجع إعادة التخطيط:** Issue #331  
**مرجع إعدادات المدير:** Issue #320

## 1. الغرض

منع الخلط بين وجود كود في المستودع وبين اعتماد القدرة للاستخدام الفعلي. وجود وحدة أو مسار API أو اختبار ناجح لا يثبت وحده اكتمال التفويض، سلامة التشغيل السريري، أو الجاهزية للإنتاج.

## 2. حدود معتمدة يجب احترامها

تستبعد `docs/07-التنفيذ/EXEC-0006-الأساس-الصحي.md` صراحةً مفاهيم التشخيص والطبيب والدواء/Medication وLab Test والحساب الصحي والقرارات السريرية الذاتية أو سلطة الذكاء الاصطناعي السريرية. لا تُرفع هذه الاستثناءات بتعديل فني أو باختيار في واجهة إعدادات المدير؛ يلزم قرار نطاق رسمي من الجهة المخولة.

كما أن قرار إعدادات المدير لا يغيّر السياسات المالية المعلّقة تلقائيًا، ولا يحوّل التوصية إلى سياسة نشطة.

## 3. جرد ما يحتاج بوابة تشغيل

يحتوي مجلد `hospital/` على نموذج تطوير مستقل، وتصف وثائقه وحداته ومساراته بأنها تشمل بعض أو كل ما يلي:

- المرضى والمواعيد والأطباء.
- اللقاءات والسجلات السريرية.
- أوامر المختبر والنتائج.
- الأدوية والوصفات والصرف والمخزون.
- الأسرة والتنويم.
- الفواتير والمدفوعات.

هذا الجرد **ليس إقرارًا باعتماد هذه القدرات**. يجب مراجعة كل مسار فعليًا، بما فيه المسارات الموجودة على `main`، لا مراجعة PR #272 وحده.

## 5. بوابة قبول أي مسار إداري جديد

لا يعلن المسار جاهزًا للدمج أو للاستخدام التشغيلي حتى تتوفر الأدلة التالية:

1. **النطاق:** ارتباط موثق بمتطلب/قرار معتمد، مع ذكر الاستثناءات.
2. **الهوية والتفويض:** اشتقاق هوية المنفذ من جلسة موثوقة، وفحص صلاحية الخادم لكل عملية وكيان؛ لا يكفي رمز مشترك أو إخفاء زر في الواجهة.
3. **الاستمرارية:** تخزين دائم وترحيل قابل للاختبار على قاعدة فارغة وأخرى تحتوي بيانات.
4. **سلامة المعاملات:** معاملات ذرية، وقيود قاعدة بيانات حيث أمكن، واختبارات تعارض وتزامن وإعادة محاولة.
5. **تاريخ موثوق:** تسجيل الفاعل والوقت ونوع العملية والنتيجة والتغييرات الضرورية، مع فشل مغلق إذا تعذر تسجيل حدث التدقيق الإلزامي.
6. **الواجهة:** لا تحفظ بيانات المرضى أو الأدلة الحساسة في `localStorage`؛ رسائل عربية واضحة وإتاحة أساسية.
7. **الاختبارات:** نجاح مجموعة Python وStage 7 على SHA النهائي نفسه، مع اختبارات سلبية للصلاحيات والتعارض والفشل.
8. **التشغيل:** توثيق الأسرار والنسخ الاحتياطي والاستعادة والمراقبة وحدود الاستخدام.
9. **المراجعة:** عدم دمج طلب متعارض مع النطاق أو لا يمكن التحقق من اختباره.

## 6. متطلبات شاشة إعدادات المدير

يجب أن تعرض الشاشة لكل خيار:

- اسم النشاط ونطاق التأثير.
- الحالة: مقترح، بانتظار المراجعة، معتمد، مرفوض، أو مفعّل.
- أثر التغيير والوظائف التابعة والمخاطر.
- الجهة المخولة بالقرار وما إذا كان القرار البشري مطلوبًا.
- إصدار الإعدادات الحالي، وسبب التغيير، وسجل القرار.

يجب أن تكون العمليات منفصلة: قراءة السياق ← اقتراح ← مراجعة/اعتماد أو رفض ← تفعيل مضبوط الإصدار. لا يفعّل اختيار «الصحة» أو «مختلط» أو أي نشاط وظائف سريرية مستثناة، ولا يسمح للمدير بتجاوز صلاحياته.

## 7. العمل التالي

1. مراجعة مسارات `hospital/api.py` وعمليات `hospital/workflows.py` مقابل مصفوفة النطاق والتفويض، مع اختبار كل مسار.
2. تحديد ما يجب حجبه افتراضيًا إلى أن تُستوفى متطلبات الاعتماد، دون كسر مسارات أخرى بصمت.
3. استخراج شريحة المواعيد/التنويم الإدارية فقط، وإعادة استخدام عقود الهوية والتفويض والتاريخ الموجودة.
4. بناء API إعدادات المدير بعد حسم مكانه في معمارية التطبيق ونموذج الهوية والصلاحيات.
5. إبقاء PR #272 مسودة حتى يعالج تعارض النطاق، وليس فقط خطأ تتبع التنفيذ.

## 8. إعلان الحالة

هذه الوثيقة تحسن وضوح النطاق ولا تنفذ بوابة تشغيل برمجية بمفردها. لا تعتبر أي قدرة سريرية أو مالية معتمدة بسبب ورودها في الجرد. أي ادعاء عن جاهزية التشغيل يجب أن يستند إلى كود، واختبارات، ومراجعة نطاق على النسخة النهائية نفسها.
