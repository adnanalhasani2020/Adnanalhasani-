# التحقق الآلي والـCI — Stage 7

## اسم الـWorkflow
**Stage 7 Automated Tests**

المسار:
.github/workflows/stage7-tests.yml

## ماذا يختبر؟
يشغّل الـworkflow جميع اختبارات pytest الموجودة تحت tests/، بما فيها:
- tests/test_stage7_batch1.py
- tests/test_batch2.py
- tests/test_batch3.py
- tests/test_batch4.py
- tests/test_stage7_ci_coverage.py

ويستخدم test_stage7_ci_coverage.py تحققاً خفيفاً يكتشف ملفات Python الحالية تحت src/agent_core/ ويستورد كل وحدة منها، مع استثناء __init__.py فقط لأنه ملف تهيئة الحزمة وليس وحدة تنفيذ مستقلة.

لا يوجد framework اختبار جديد ولا يتم تعديل اختبارات Stage 7 القائمة لإخفاء الفشل.

## متى يعمل؟
- عند push إلى main.
- عند pull_request إلى main.

البيئة:
- Ubuntu runner.
- Python 3.11.9.
- تثبيت المشروع من pyproject.toml.
- تثبيت pytest صراحةً لأنه ليس dependency حالياً.

## تفسير PASS / FAIL
- PASS: نجح تثبيت المشروع وpytest واجتازت مجموعة الاختبارات التي جمعها pytest دون فشل.
- FAIL: يوجد فشل في الاختبارات أو في إعداد البيئة/التثبيت؛ يجب قراءة أول traceback والتمييز بين فشل البيئة وفشل الكود قبل أي تعديل.
- لا تُعتبر إضافة الـworkflow بحد ذاتها دليلاً على PASS؛ نتيجة تشغيل GitHub Actions الفعلية هي التي تثبت تشغيل CI.

## حدود التحقق
GitHub Actions هو مصدر تحقق آلي للاختبارات فقط. ليس مصدراً لـDomain Truth، ولا يغيّر Source of Truth، ولا يحسم DEC-0001..DEC-0013، ولا يفتح Stage 8.

## حالة التنفيذ
تمت إضافة الـworkflow واختبار تغطية الوحدات إلى Stage 7. لا يُسجّل نجاح تشغيل CI إلا بعد ظهور تشغيل فعلي ناجح في GitHub Actions.
