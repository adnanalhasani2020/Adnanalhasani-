# EXEC-0029 — Persisted Role Assignment records

## Evidence of gap
The relational schema already defines `role_assignments` with a Membership foreign key, caller-supplied `role_code`, existing state constraint (`active`, `suspended`, `ended`), effective period, timestamps, and version. The prior Activity/Membership application path did not provide explicit persisted Role Assignment create/read/list operations.

## Implemented capability
- Persist a caller-supplied Role Assignment referencing an existing Membership.
- Restore a Role Assignment by identifier.
- List assignments for one Membership in deterministic `created_at, role_assignment_id` order.
- Validate UUIDs, required role code, existing schema states, timezone-aware timestamps, and effective-period ordering.
- Reuse the existing schema without migration.

## Boundaries
- This is explicit record persistence only; no lifecycle transitions or role vocabulary are invented.
- It does not create Memberships or infer permissions, authorization, or access from a Role Assignment.
- No automatic Role Assignment is created by invitations or Membership operations.
- No authorization grant, notification, or other domain side effect is introduced.

## Implementation and tests

- Tests: `tests/test_stage43_role_assignment_persistence.py`
- Coverage: persistence/reopen, deterministic membership-scoped listing, missing records/references, invalid UUID/state/role/timestamp inputs, effective-period ordering, and database foreign-key enforcement.
