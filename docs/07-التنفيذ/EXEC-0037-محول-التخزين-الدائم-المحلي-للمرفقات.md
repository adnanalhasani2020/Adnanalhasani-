# EXEC-0037 — محول التخزين الدائم المحلي لمحتوى المرفقات

## الهدف
تطبيق واجهة `ContentStore` الحالية على نظام الملفات المحلي، مع الحفاظ على مخطط البيانات الوصفية دون تغيير.

## العقد والتنفيذ
- يضيف `LocalFilesystemContentStore` واجهتي `put(bytes) -> storage_ref` و`get(storage_ref) -> bytes`.
- المراجع من الشكل `localfs://<32 lowercase hex>`، ويُولّد المعرّف داخليًا؛ لا يُستخدم اسم الملف أو مرجع يقدمه المستدعي كمسار.
- يُحصر الوصول في مجلد التخزين المفتوح كدليل، وتُرفض المراجع غير المطابقة والملفات الهدف ذات الروابط الرمزية. تُستخدم مقابض دليل و`O_NOFOLLOW` حيث تدعمها المنصة.
- تكتب البايتات إلى ملف مؤقت حصري داخل المجلد، ويُزامن الملف قبل نشره. بعد ذلك تنشر `os.replace` الملف ذريًا داخل الدليل نفسه.
- إذا فشلت الكتابة قبل النشر أو فشلت `os.replace`، لا يعاد مرجع كائن مكتمل؛ يجري تنظيف الملف المؤقت غير المنشور عند الإمكان.
- إذا نجح `os.replace` ثم فشلت مزامنة الدليل بخطأ لا يُصنف ضمن قيود المنصة المعروفة، يرفع المحول `ContentPublishedDurabilityError` حاملًا `storage_ref`. يعني ذلك أن الكائن نُشر، لكن متانة إدخال الدليل لم تتأكد؛ لا يجوز تفسيره على أنه فشل قبل النشر أو نجاح دائم كامل.
- يحوّل `FileAttachmentContentApplication` هذا الخطأ إلى `ContentStorageFailure` مع الحفاظ على `storage_ref`، ولا يحاول تسجيل metadata ولا يحذف المحتوى ولا يعيد المحاولة تلقائيًا.
- لا يحسب المحول الحجم أو SHA-256 ولا يكرر فحص السلامة؛ تبقى هذه مسؤولية `FileAttachmentContentApplication`.
- فشل metadata بعد عودة التخزين بنجاح يبقى `PartialAttachmentCreationError` مع المرجع، دون حذف أو إعادة محاولة.

## الإعداد والتشغيل
- متغير البيئة: `AGENT_ATTACHMENT_CONTENT_STORE`.
- اسم الإعداد في `Settings`: `attachment_content_store_path`.
- الافتراضي للتطوير: `.agent_core/attachments`. هذا مسار افتراضي فقط وليس ضمانًا للاستمرارية في الحاويات أو بيئات النشر.
- على المشغل توفير مجلد قابل للكتابة بواسطة حساب التطبيق، وقراءة الملفات التي أنشأها، ومساحة قرص كافية، مع حماية المجلد من التعديل بواسطة مستخدمين غير موثوقين.
- الاستمرارية عبر العمليات تتطلب استخدام المسار نفسه ومجلدًا يبقى موجودًا بعد إعادة تشغيل العملية. لا يضمن المحول توفر الملف بعد فقدان القرص أو تلف نظام الملفات، ولا يوفر نسخًا احتياطيًا أو تكرارًا أو مشاركة بين المضيفين.
- ضمان إعادة التسمية الذرية يعتمد على دعم نظام الملفات للعملية داخل المجلد نفسه. لا تعني مزامنة الملف والدليل ضمانًا مطلقًا ضد أعطال العتاد أو كل أنظمة الملفات. عند فشل مزامنة الدليل بعد النشر، يحتفظ الخطأ بالمرجع المنشور كي يمكن تتبع الكائن مع بقاء متانة النشر غير مؤكدة.

## الاختبارات
`tests/test_stage49_file_attachment_filesystem_store.py` يغطي الاسترجاع بمحول جديد، والاسترجاع عبر عمليتين منفصلتين تستخدمان قاعدة البيانات ومجلد المحتوى نفسيهما، وفشل الكتابة دون metadata، ونجاح النشر ثم فشل مزامنة الدليل مع الاحتفاظ بالمرجع، وفشل metadata الجزئي دون حذف تعويضي، وفقدان المحتوى، وتلفه، ومراجع المسارات غير الموثوقة، والروابط الرمزية، وقراءة إعداد المسار.

## الحدود
- لا تغيير لمخطط قاعدة البيانات أو اعتماد خارجي أو مزود تخزين خارجي.
- لا حذف تعويضي للمحتوى المنشور، ولا إعادة محاولة تلقائية، ولا سياسة احتفاظ أو حذف تلقائي.
- لا صلاحيات مرفقات أو تشفير أو نسخ احتياطي أو معالجة orphan objects.
- يظل `InMemoryContentStore` متاحًا للاختبارات والتكامل غير الدائم.
