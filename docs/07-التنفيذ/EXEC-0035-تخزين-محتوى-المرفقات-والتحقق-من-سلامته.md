# EXEC-0035 — تخزين محتوى المرفقات والتحقق من سلامته

## الهدف
إضافة مسار تطبيق مستقل لتخزين بايتات المرفق واسترجاعها مع التحقق من سلامتها، مع الحفاظ على سجل البيانات الوصفية الموجود دون تغيير مخططه.

## العقد
- `ContentStore` واجهة محايدة قابلة للاستبدال: `put(bytes) -> storage_ref` و`get(storage_ref) -> bytes`.
- `InMemoryContentStore` محول محلي اختباري غير دائم؛ لا يعتمد على خدمة خارجية ولا يُقدَّم بوصفه تخزينًا إنتاجيًا دائمًا.
- يحسب التطبيق `size_bytes` وSHA-256 من البايتات الفعلية؛ ولا يقبل قيمًا محسوبة من المستدعي.
- تُخزن البايتات أولًا ثم يُنشأ سجل metadata باستخدام المرجع والحجم والبصمة المحسوبة. النجاح النهائي يعني نجاح المرحلتين.
- فشل الكتابة إلى مخزن المحتوى ينتج `ContentStorageFailure` ولا ينشئ سجلًا وصفيًا.
- فشل تسجيل metadata بعد تخزين المحتوى ينتج `PartialAttachmentCreationError` مع `storage_ref`. يبقى المحتوى كما هو، بلا حذف تعويضي أو إعادة محاولة تلقائية.
- الاسترجاع يتحقق من نوع البايتات وحجمها ثم SHA-256 قبل إرجاعها. فشل الوصول ينتج `ContentRetrievalError`، وفشل المطابقة ينتج `ContentIntegrityError`.
- مرجع التخزين لا يثبت وحده وجود المحتوى أو سلامته.

## التحقق
`tests/test_stage47_file_attachment_content.py` يغطي round-trip، والحجم والبصمة المحسوبين، وفشل التخزين، والفشل الجزئي في metadata، وغياب المحتوى، وعدم تطابق الحجم أو البصمة، والاستمرارية مع إعادة فتح قاعدة البيانات باستخدام محول التخزين نفسه، والتوافق مع سجل metadata الحالي.

## الحدود
- لا ترحيل schema ولا سجل حالات جديد.
- لا حذف تعويضي، ولا إعادة محاولة تلقائية، ولا صلاحيات أو سياسات احتفاظ.
- لا تكامل خارجي أو افتراض دوام `InMemoryContentStore` عبر إعادة تشغيل العملية.
- إذا فشل حفظ metadata، فإن مرجع التخزين المعاد في الخطأ للتتبع فقط، ولا يعني أن إنشاء المرفق نجح.
