# EXEC-0020 — Persisted Pending Operation queue lifecycle

## Evidence of gap
- `SPEC-0019-offline-pending-finality.md` explicitly defines Pending Operation as operational and non-final, separate from Owner Domain truth.
- `schema/migrations/0001_initial_relational_schema.sql` already defines `pending_operations` with device ownership, unique `namespace + operation_id`, request metadata, timestamps, and constrained persisted states (`queued`, `submitted`, `finalized`, `rejected`, `conflicted`, `cancelled`).
- `src/agent_core/domain_offline.py` had only in-memory Device and PendingOperation records; no application path persisted the existing queue contract.

## Implemented capability
- Queue a pending operation only for an existing active Device.
- Enforce idempotent reuse of the same `namespace + operation_id` only when device, operation kind, and request fingerprint match.
- Persist `queued -> submitted -> cancelled` transitions, with idempotent repeat requests and fail-closed invalid transitions.
- On Device loss, atomically mark the Device lost with optimistic `version_no` checking and cancel all queued/submitted operations for that Device.
- Retrieve one operation and list operations for a Device in deterministic order.

## Explicit boundary
- Pending operations remain operational records, not Domain Truth.
- This path does not execute domain effects, finalize or reject owner-domain outcomes, resolve conflicts, add financial/health/commerce finality, or introduce a synchronization protocol.
- Persisted `finalized` and `rejected` states are intentionally not writable here because no Owner Domain acceptance/rejection contract is implemented by this path.
- No schema migration is required; the implementation uses the existing table and constraints.

## Tests
`tests/test_stage35_pending_operation_persistence.py` covers persistence across reopen, duplicate-key binding, active-device requirements, transition idempotency, device-loss cancellation, and optimistic version checks.
