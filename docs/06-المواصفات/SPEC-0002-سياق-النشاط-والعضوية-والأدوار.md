# SPEC-0002 — سياق النشاط والعضوية والأدوار

## 1. Purpose / Scope

تحدد هذه المواصفة السلوك الدلالي الأساسي لمجال **Activities & Roles** فيما يخص:
- **Activity** كنشاط تجاري/خدمي مستقل.
- **Organization** ككيان مؤسسي يمكن أن يدير أنشطة متعددة دون مساواته بالنشاط نفسه.
- **Membership** كعلاقة تربط **Person** بسياق النشاط.
- **Role Assignment** كإسناد دور داخل سياق النشاط.
- علاقة الشخص بالنشاط عبر Membership، ثم وصف مسؤولياته السياقية عبر Role Assignment.
- التمييز بين Owner وManager وEmployee بوصفها أدواراً أو حالات علاقة سياقية، لا هويات أو Concepts مستقلة.
- الحفاظ على الحدود بين النشاط والهوية والتفويض والحقيقة المالية.

هذه مواصفة سلوكية/دلالية. لا تحدد قاعدة بيانات أو SQL أو API أو واجهة مستخدم أو Framework أو Provider أو خوارزمية مزامنة.

المبدأ المركزي هو:

**Person هو الهوية؛ Activity هو السياق؛ Membership هي العلاقة؛ Role Assignment هو الدور؛ Authorization هو قرار الصلاحية.**

لا تنقل هذه المواصفة ملكية Authorization إلى Role Assignment، ولا تنقل ملكية Financial Account إلى Activities.

**المراجع الأساسية:** Stage 3: متطلبات الأنشطة والمؤسسات والموظفين؛ Stage 4: `02-حدود-المجالات.md` و`03-السياقات-والحدود-Context-Boundaries.md` و`05-معمارية-الأنشطة-والأدوار.md`؛ Stage 5: `03-الكيانات-المفاهيمية.md` و`04-العلاقات-المفاهيمية.md` و`06-الأنشطة-الأدوار-والعضويات.md`.

## 4. Concepts Used

المفاهيم المستخدمة هنا هي مفاهيم Stage 5 فقط:

- **Person:** الشخص/الجهة ذات الهوية الدائمة؛ ملكية الحقيقة لدى Identity.
- **Activity:** نشاط تجاري/خدمي مستقل؛ ملكية الحقيقة لدى Activities.
- **Organization:** كيان مؤسسي؛ ملكية الحقيقة ضمن Activities.
- **Membership:** علاقة Person بنشاط؛ ملكية حقيقة العلاقة لدى Activities.
- **Role Assignment:** إسناد دور داخل سياق؛ ملكية حقيقة الإسناد لدى Activities.
- **Authorization:** قرار صلاحية مستقل؛ ملكية القرار لدى Authorization.
- **Authorization Grant:** أساس/منحة للسلطة وفق نموذج التفويض؛ لا تملكه Role Assignment.
- **Financial Account:** حقيقة مالية مستقلة؛ ملكيتها لدى Finance.
- **Provenance:** وصف أصل/إنتاج/تعديل المعلومة عند الحاجة.
- **Audit Record:** سجل رقابي للفعل أو القرار عند الحاجة.
- **Agent:** مفهوم قائم في Stage 5؛ لا يصبح Person أو Role Assignment أو Domain Owner.

### مصطلحات ليست Concepts هنا

لا تنشئ هذه المواصفة مفاهيم باسم:
- Employee.
- Owner.
- Manager.
- User.
- Actor.

**Employee** وصف لشخص يحمل Membership وRole Assignment مناسبين داخل Activity/Organization، وليس Concept مستقلاً.

**Owner / Manager** أوصاف لدور أو حالة علاقة سياقية وفق النموذج القائم، وليست Concepts مستقلة.

**User** ليس بديلاً عن Person.

**Actor** لا يعاد إلى Stage 5؛ لا تستخدم هذه المواصفة Actor كمفهوم بديل.

## 5. Preconditions

قبل تفسير أو تغيير حالة مرتبطة بالنشاط يجب أن يكون السياق واضحاً:

1. Person هو مرجع الهوية البشرية، وليس Activity أو Membership أو Role Assignment.
2. Activity هو السياق الذي تُفسر داخله العلاقة والدوْر.
3. Organization لا تُفترض مساواتها بـActivity.
4. Membership موجودة عندما يكون المطلوب وصف علاقة Person بالنشاط.
5. Role Assignment لا يفترض وجوده إلا عندما يوجد سياق عضوية صالح أو علاقة تسمح به وفق النموذج القائم.
6. الدور لا يُقرأ كقرار Authorization.
7. Financial Account لا يُستنتج من Membership أو Role Assignment.
8. أي معنى قانوني للملكية أو العمل أو الموظف لا يُستنتج خارج ما حُسم في Stage 3–5.
9. DEC-0001 يبقى مفتوحاً، ولا تستخدم هذه المواصفة لحسم الولاية أو السوق.
10. أي قرار صلاحية تفصيلي يُحال إلى Authorization / SPEC-0003.

## 6. Activity Context

**Activity** هو نشاط تجاري/خدمي مستقل ضمن حدود Activities.

الحالات المفاهيمية المثبتة في Stage 5:
- تأسيس.
- فعال.
- متوقف.
- منته.

السلوك الدلالي:

1. Activity تمثل سياقاً مستقلاً يمكن أن ترتبط به Memberships وRole Assignments.
2. Activity لا تنشئ Person جديداً لمجرد انضمام شخص إليها.
3. Activity لا تساوي Organization.
4. Activity لا تساوي Authorization.
5. Activity لا تملك Financial Account لمجرد أن لها علاقة مالية أو تشغيلية به.
6. Activity يمكن أن يكون لها أشخاص متعددون في Memberships مختلفة.
7. Person واحد يمكن أن يظهر في Activities متعددة دون إنشاء Person جديد.
8. انتهاء Activity لا يمحو Membership أو Role Assignment التاريخيين.
9. توقف Activity لا يحوّل Role Assignment إلى Authorization.
10. وجود Activity لا يعني أن كل Person مرتبط بها يملك صلاحية مطلقة.

**مرجع Stage 4:** Activities تملك حقيقة النشاط المؤسسي/التشغيلي وعلاقاته الوظيفية.

**مرجع Stage 5:** Activity مفهوم مستقل عن Organization، وقد يضم Organization وOffering وMembership.

## 7. Organization Context

**Organization** مفهوم مؤسسي مستقل داخل حدود Activities.

الحالات المفاهيمية المثبتة:
- تأسيس.
- فعال.
- منحل.

القواعد:

1. Organization ليست مرادفاً لـActivity.
2. Activity ليست مرادفاً لـOrganization.
3. Organization قد تدير أنشطة متعددة وفق النموذج القائم.
4. وجود Organization لا ينشئ Person.
5. Person قد يحمل Memberships في Activities مرتبطة بسياقات مؤسسية مختلفة.
6. كون الشخص مرتبطاً بـOrganization لا يحوله إلى Employee كمفهوم مستقل.
7. كون الشخص Owner أو Manager في سياق مؤسسي لا يمنحه Authorization مطلقة.
8. Organization لا تصبح مالكة للحقيقة المالية لمجرد إدارة نشاط؛ Financial Account يبقى لدى Finance.
9. أي معنى قانوني للملكية المؤسسية يتأثر بالولاية/السوق ولا يُحسم هنا.

**مرجع Stage 5:** Organization كيان مؤسسي قد يدير أنشطة متعددة، ومالكه الدوميني Activities.

## 8. Membership Lifecycle

**Membership** هي علاقة Person بالنشاط، وليست Person ولا Role Assignment.

الحالات المثبتة في Stage 5:
- مقترحة.
- فعالة.
- موقوفة.
- منتهية.

وتستخدم الفترة الزمنية `start/end` عندما يكون لها معنى.

### إنشاء Membership

عند إنشاء Membership:
1. لا يُنشأ Person جديد.
2. لا تُنشأ Authorization تلقائياً.
3. لا يُنشأ Financial Account.
4. لا تصبح Membership دوراً بحد ذاتها.
5. تُسجل العلاقة ضمن Activity context.

### تفعيل Membership

Membership الفعالة تعني أن علاقة Person بالنشاط فعالة ضمن سياقها وفترتها.

لا تعني:
- صلاحية مطلقة.
- ملكية كل بيانات النشاط.
- ملكية Financial Account.
- دور Manager أو Owner ما لم يوجد Role Assignment مناسب.

### تعليق Membership

تعليق Membership يوقف أثر العلاقة الحالي وفق سياقها، مع بقاء التاريخ.

لا يمحو:
- Person.
- Activity.
- Membership history.
- Role Assignments التاريخية.

### انتهاء Membership

انتهاء Membership يوقف العلاقة الفعالة وفق نطاقها، ولا ينهي Person.

Role Assignments التابعة للسياق لا تُقرأ كأدوار فعالة بعد انتهاء الأساس الزمني المناسب؛ ومع ذلك لا يُمحى تاريخها.

## 9. Role Assignment Lifecycle

**Role Assignment** هو إسناد دور داخل سياق، وليس Authorization.

الحالات المثبتة في Stage 5:
- assigned.
- active.
- revoked.
- expired.

ويستخدم `effective/expiry` عندما يكون للزمن معنى.

### إنشاء الإسناد

عند إنشاء Role Assignment:
1. لا ينشأ Person.
2. لا تتحول Membership إلى Authorization.
3. لا تمنح صلاحية مطلقة.
4. لا تنشئ Financial Account.
5. لا تنشئ Employee كـConcept.
6. لا تنشئ Owner أو Manager كـConcept.

### تفعيل الإسناد

Role Assignment فعال يصف أن الشخص يحمل الدور المحدد في السياق المحدد خلال الفترة الفعالة.

يمكن أن يكون للشخص أدوار متعددة إذا كان ذلك ممثلاً زمنياً وسياقياً في النموذج القائم.

### تعليق/سحب/انتهاء الإسناد

تعليق أو سحب أو انتهاء Role Assignment يوقف أثر الدور الحالي دون حذف التاريخ.

انتهاء الدور لا يعني:
- انتهاء Person.
- انتهاء Membership بالضرورة.
- انتهاء Activity.
- إلغاء Financial Account.
- منح أو سحب Authorization تلقائياً ما لم يقرر Authorization ذلك في نطاقه.

## 10. Person ↔ Activity Relationship

العلاقة الأساسية هي:

**Person ↔ Membership ↔ Activity**

وهي علاقة **M:N** مثبتة في Stage 5.

القواعد:

1. Person واحد يمكن أن تكون له Memberships متعددة في Activities متعددة.
2. Activity واحدة يمكن أن ترتبط بأشخاص متعددين عبر Memberships.
3. Membership هي التي تحمل حقيقة العلاقة السياقية؛ لا يحل Role Assignment محلها.
4. Person لا يصبح Activity بمجرد العضوية.
5. Activity لا تصبح Person بمجرد وجود عضو.
6. Activity لا تنشئ هوية جديدة لكل Person.
7. اختلاف الدور بين نشاطين لا ينشئ Person ثانياً.
8. انتهاء Membership لا ينهي Person.
9. Person يمكن أن يكون Customer في Activity وEmployee في Activity أخرى؛ لا يوجد Concept جديد اسمه Employee.
10. السياق يميز معنى العلاقة دون إعادة تعريف الهوية البشرية.

**مرجع Stage 5:** Person ↔ Activity عبر Membership: M:N، وPerson لا يتكرر بسبب النشاط.

## 11. Membership ≠ Role Assignment

الفصل إلزامي:

| المفهوم | السؤال الذي يجيب عنه | المالك |
|---|---|---|
| Membership | هل توجد علاقة Person بالنشاط، وما حالتها وفترتها؟ | Activities |
| Role Assignment | ما الدور المسند للشخص داخل ذلك السياق، وما حالته وفترته؟ | Activities |
| Authorization | ما الذي يجوز فعله في سياق وغرض محدد؟ | Authorization |

النتائج:

- Membership قد تكون فعالة دون Role Assignment فعال.
- Role Assignment يصف دوراً سياقياً ولا يستبدل Membership.
- تغيير الدور لا يعني بالضرورة إنشاء Membership جديدة.
- انتهاء الدور لا يعني بالضرورة انتهاء Membership.
- انتهاء Membership يمنع قراءة الدور كسياق فعال إذا لم يعد أساس العلاقة صالحاً.
- لا تتحول Membership إلى Authorization بمجرد التفعيل.
- لا يتحول Role Assignment إلى Authorization بمجرد أن يكون الدور اسمه Manager أو Owner.

**مرجع Stage 5:** Membership ↔ Role Assignment: 1:N، وكل إسناد له فترة فعالية مستقلة.

## 12. Role Assignment ≠ Authorization

Role Assignment يجيب:

> **ما الدور الذي أُسند إلى الشخص داخل نشاط/سياق؟**

Authorization تجيب:

> **ما الذي يُسمح لهذا الفاعل بفعله في سياق وغرض محدد؟**

لذلك:

1. Role Assignment لا يمنح Authorization تلقائياً.
2. Role Assignment قد يكون مدخلاً لتقييم Authorization.
3. Authorization قد تقرر صلاحية محددة أو مقيدة أو مؤقتة.
4. وجود Manager لا يعني صلاحية مطلقة.
5. وجود Employee لا يعني صلاحية تنفيذ كل فعل.
6. وجود Owner كدور سياقي لا يعني امتلاك كل حقيقة مالية أو كل بيانات الأفراد.
7. SPEC-0002 لا يحدد سياسة Authorization التفصيلية.
8. SPEC-0003 يملك قرار Authorization.

**مرجع Stage 4:** Authorization يملك قرار الصلاحية، وActivities تملك العلاقة والدور.

**مرجع Stage 5:** Role Assignment ↔ Authorization Grant علاقة 0:N؛ الدور قد يكون أساس تقييم ولا يملك المنحة.

## 13. Owner / Manager / Employee Distinctions

هذه الأوصاف لا تنشئ Concepts جديدة.

### Owner

Owner وصف لدور/علاقة سياقية عندما يكون هذا المعنى موجوداً في النشاط.

لا يعني تلقائياً:
- Person جديد.
- Organization جديد.
- Financial Account ownership.
- Authorization مطلقة.
- حقاً قانونياً عاماً صالحاً لكل ولاية.

### Manager

Manager وصف لدور سياقي.

Manager قد تكون له مسؤوليات داخل Activity، لكن اسم الدور لا يحدد وحده ما يجوز فعله.

### Employee

Employee وصف لشخص داخل نشاط عندما تحمل Membership وRole Assignment المعنى المناسب لذلك السياق.

Employee ليس Concept في Stage 5.

### User / Person

User ليس Concept جديداً هنا. عندما يكون المقصود هو الإنسان، المرجع المفاهيمي هو Person.

### Owner ≠ Manager ≠ Employee كـConcepts

يمكن أن تكون هذه الأوصاف مختلفة داخل نشاط واحد أو عبر أنشطة متعددة، لكن لا تُنشئ هويات مستقلة.

**مرجع Stage 4:** `05-معمارية-الأنشطة-والأدوار.md` يثبت Employee ≠ Owner وActivity ≠ Employee.

## 14. قواعد الموظف داخل النشاط

عندما يكون Person موظفاً داخل Activity بالمعنى السياقي:

1. يظل Person هو الهوية.
2. Membership تمثل العلاقة بالنشاط.
3. Role Assignment يصف الدور المناسب.
4. لا ينشأ Employee Concept.
5. لا يصبح Person مالكاً لكل حقيقة النشاط.
6. لا يصبح Person مالكاً لـFinancial Account لمجرد دوره.
7. لا يحصل على Authorization مطلقة من الاسم الوظيفي.
8. الأفعال خارج نطاق الدور لا تصبح مشروعة لمجرد كون الشخص موظفاً.
9. أي صلاحية فعلية تحتاج قرار Authorization في سياقها.
10. القيود الخاصة ببيانات الأفراد لا تُستنتج من ملكية النشاط أو الاسم الوظيفي وحده.

**REQ-FUNC-0009:** Primary هي SPEC-0003؛ SPEC-0002 يحدد فقط سياق العلاقة والدور الذي قد يدخل في التقييم.

**REQ-FUNC-0010:** Primary هي SPEC-0003؛ فصل سياق النشاط عن بيانات الأفراد لا يتحول هنا إلى سياسة خصوصية أو Authorization تفصيلية.

## 15. قواعد تعدد الأنشطة للشخص نفسه

Person واحد يمكن أن يحمل Memberships متعددة عبر Activities مختلفة.

أمثلة دلالية صحيحة:

1. Person يكون Employee في Activity A وCustomer في Activity B.
2. Person يحمل دور Manager في Activity A ودور مختلف في Activity B.
3. Person يحمل Membership فعالة في أكثر من Activity في الوقت نفسه.
4. Person يمكن أن يكون Customer وEmployee في Activity واحدة إذا كان النموذج السياقي يعبر عن ذلك بأدوار/علاقات قائمة.
5. اختلاف Activity لا يخلق Person جديداً.
6. اختلاف Role Assignment لا يخلق Person جديداً.
7. اختلاف Access Account لا يخلق Person جديداً، وفق الفصل الذي ثبته SPEC-0001.
8. لا يجوز استخدام نشاط واحد كدليل على أن الشخص هو النشاط أو مالكه في كل السياقات.

**مرجع Stage 4:** Invariant صريح بأن الشخص الواحد يمكن أن يكون Employee وCustomer في أكثر من Activity.

## 16. قواعد انتقال / تغيير الدور

تغيير الدور هو تغيير في Role Assignment وليس إعادة تعريف Person.

عند الانتقال من دور إلى آخر:

1. Person يبقى نفسه.
2. Activity تبقى نفسها إذا لم يتغير السياق.
3. Membership تبقى العلاقة الأساسية إذا كانت لا تزال صالحة.
4. Role Assignment السابق ينتهي/يُسحب/تنقضي فترته وفق حالته.
5. Role Assignment الجديد يمثل الدور الجديد.
6. لا يُمحى تاريخ الدور السابق.
7. لا يُستنتج من الدور الجديد Authorization جديدة إلا بقرار Authorization مستقل.
8. لا تنتقل صلاحية مالية تلقائياً مع الدور.
9. لا تُنشأ Employee/Owner/Manager Concepts.
10. أي تداخل زمني للأدوار لا يُعتبر خطأ بذاته إذا كان التداخل مقصوداً وممثلاً بفترات فعالة مستقلة.

**مرجع Stage 5:** التداخل الزمني للأدوار مسموح فقط عندما يعبر عن أدوار متزامنة مقصودة وممثلة زمنياً.

## 17. قواعد انتهاء العضوية

عند انتهاء Membership:

1. Person يبقى قائماً.
2. Activity تبقى قائمة إن لم تنتهِ لسبب آخر.
3. العلاقة الفعالة بين Person وActivity تنتهي ضمن فترة Membership.
4. Role Assignments السابقة لا تُمحى.
5. لا يصبح الشخص تلقائياً عضواً نشطاً بسبب سجل تاريخي.
6. لا ينتقل الدور إلى Activity أخرى تلقائياً.
7. لا تُنشأ Authorization جديدة.
8. لا تُلغى Financial Account تلقائياً.
9. لا يُمحى Audit أو Provenance الذي يتطلب الاحتفاظ به.
10. إذا كان هناك Membership أخرى في Activity أخرى، تبقى مستقلة.

## 18. حالات الرفض والمنع

يجب رفض أو منع الحالة الدلالية عندما تؤدي إلى خلط الحدود، ومنها:

1. اعتبار Activity هو Person.
2. اعتبار Organization هي Activity دون أساس دلالي.
3. إنشاء Person جديد لمجرد انضمامه إلى Activity.
4. إنشاء Employee Concept.
5. إنشاء Owner Concept.
6. إنشاء Manager Concept.
7. إعادة Actor كمفهوم بديل.
8. اعتبار Membership هي Role Assignment.
9. اعتبار Role Assignment هي Membership.
10. اعتبار Role Assignment هي Authorization.
11. منح صلاحية مطلقة لمجرد وجود دور Manager أو Owner أو Employee.
12. استخدام Role Assignment لإثبات ملكية Financial Account.
13. اعتبار اسم الوظيفة بديلاً عن Authorization.
14. اعتبار انتهاء Membership حذفاً لـPerson.
15. محو تاريخ Role Assignment عند تغييره.
16. جعل Activity أو Organization مالكاً لقرار Authorization.
17. جعل Activity مالكاً للحقيقة المالية.

20. إدخال سياسة Family Delegation في هذه المواصفة.

## 19. History / Provenance / Audit

تغييرات النشاط والعضوية والأدوار يجب أن تكون قابلة للتتبع عندما تكون الحاجة الدلالية أو الرقابية قائمة، دون إنشاء Concept جديد.

### Activity / Organization history

- تأسيس/تفعيل/إيقاف/انتهاء Activity لا يمحو التاريخ السابق.
- تأسيس/تفعيل/انحلال Organization لا يمحو تاريخ الأنشطة أو العلاقات.
- التغيير التصحيحي لا يساوي حذف الماضي.

### Membership history

- إنشاء Membership أو تفعيلها أو تعليقها أو إنهاؤها يبقى قابلاً للتتبع عند الحاجة.
- انتهاء Membership ليس حذفاً للعلاقة التاريخية.

### Role history

- إنشاء Role Assignment وتغييره وسحبه أو انتهاؤه يبقى قابلاً للتتبع.
- الدور السابق لا يختفي لمجرد أن دوراً جديداً أصبح فعالاً.

### Provenance / Audit

- Provenance يصف أصل/إنتاج/تعديل المعلومة، ولا يصبح مالكاً لـActivity أو Membership أو Role Assignment.
- Audit Record يوثق الفعل أو القرار عند الحاجة، ولا يصبح Domain Truth.
- Authorization history تبقى تحت ملكية Authorization.
- لا تُفرض مدد احتفاظ قانونية غير محسومة.

**مرجع Stage 5:** انتهاء العلاقات لا يمحو التاريخ، والتغيير يستخدم الفترات الزمنية والتصحيح دون حذف الماضي.

## 20. Privacy / Contextual Access Boundary

REQ-FUNC-0010 مملوك Primary لـSPEC-0003؛ لذلك تقتصر SPEC-0002 على تعريف **حدود السياق** ولا تضع سياسة Authorization تفصيلية.

القواعد:

1. Membership لا تعني حقاً عاماً في قراءة بيانات Person.
2. Role Assignment لا يعني حقاً مطلقاً في بيانات الأفراد.
3. كون Activity مملوكة أو مُدارة لا يعني تلقائياً الوصول غير المحدود إلى بيانات الأشخاص.
4. Manager ليس بديلاً عن قرار Authorization.
5. Employee ليس بديلاً عن قرار Authorization.
6. Owner ليس بديلاً عن قرار Authorization.
7. الوصول إلى البيانات يظل سياقياً ويخضع لقرار السلطة في مجاله.
8. الولاية/السوق والقطاع قد تؤثر في القيود؛ DEC-0001 لا يُحسم هنا.

**مرجع Stage 3:** REQ-FUNC-0010 يفصل ملكية النشاط عن بيانات الأفراد ويذكر اعتماد Q-0002/Q-0027 وDEC-0001.

## 21. Offline Boundaries

**Offline Operation ≠ Domain Finality.**

في سياق Activities & Roles:

1. الحالة المحلية لا تنقل Source of Truth من Activities.
2. Device لا يصبح مالكاً لـActivity أو Membership أو Role Assignment.
3. Pending Operation لا تصبح Domain Truth لمجرد وجودها محلياً.
4. Conflict لا يصبح مالكاً للحقيقة المتعارضة.
5. فقدان الاتصال لا يثبت أن Membership أو Role Assignment أصبح نهائياً.
6. لا تحدد هذه المواصفة خوارزمية Sync أو Conflict Resolution.
7. الحسم النهائي يبقى لدى Owner Domain للحقيقة الأصلية.
8. لا تنشئ Offline حالة Person أو Employee أو Owner أو Manager جديدة.

**مرجع Stage 4:** Offline علاقة تشغيلية مع Finality، والحقيقة تبقى لدى المجال الأصلي.

## 22. Agent Boundaries

Agent ليس Person ولا Role Assignment ولا Domain Owner لمجرد كونه Agent.

القواعد:

1. Agent قد يعمل داخل سياق Activity عندما تكون السلطة المقررة تسمح بالفعل.
2. Agent لا يصبح عضواً أو صاحب دور لمجرد تنفيذ فعل.
3. Agent لا ينشئ Membership أو Role Assignment كحقيقة نهائية من ذاته.
4. Agent لا يصبح Owner للحقيقة الدومينية.
5. Agent لا يمنح Authorization لنفسه.
6. أي سلطة فعلية للوكيل تُحسم في SPEC-0017 وما يرتبط بـAuthorization / Authority Policy.
7. Agent Action لا ينقل Source of Truth من Activities أو من المجال المتأثر بالفعل.
8. لا تستخدم هذه المواصفة DEC-0006/DEC-0007 لإدخال قرار جديد.

**مرجع Stage 4:** Agents يستهلكون السلطة ولا يملكون الحقيقة الأصلية.

## 23. Source of Truth

| الحقيقة | Source of Truth | ما لا يجوز استنتاجه |
|---|---|---|
| Person | Identity | لا تصبح ملكية النشاط |
| Activity | Activities | لا تصبح Authorization |
| Organization | Activities | لا تساوي Activity تلقائياً |
| Membership | Activities | لا تصبح Role Assignment أو Authorization |
| Role Assignment | Activities | لا يصبح Authorization |
| Authorization decision | Authorization | لا يملكها Role Assignment |
| Financial Account | Finance | لا تنتقل إلى Activities بسبب دور شخص |
| Audit Record | Audit | لا يصبح Domain Truth |
| Provenance | بحسب الحقيقة التي يصفها | لا يستبدل Owner Domain |

القواعد:

- **Activity owns its activity-domain truth.**
- **Membership owns membership relationship truth** ضمن ملكية Activities الدومينية.
- **Role Assignment owns role-assignment truth** ضمن ملكية Activities الدومينية.
- **Authorization owns authorization decision.**
- **Finance owns Financial Account.**
- **Identity owns Person truth.**

القراءة أو الإشارة بين المجالات لا تنقل الملكية.
