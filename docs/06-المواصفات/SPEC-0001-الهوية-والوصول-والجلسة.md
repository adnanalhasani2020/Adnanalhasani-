# SPEC-0001 — الهوية والوصول والجلسة

## 1. Purpose / Scope

تحدد هذه المواصفة السلوك الدلالي الأساسي لمجال **Identity / Access** فيما يخص:
- تمثيل الشخص/الجهة كـ **Person**.
- تمييز **Identifier** عن الشخص وعن المصادقة.
- تمثيل **Access Account** كسياق وصول مستقل عن الهوية البشرية وعن الحساب المالي.
- ربط **Authenticator** بحساب الوصول دون اعتباره الشخص نفسه.
- تمثيل **Session** كسياق وصول مؤقت لا يتحول إلى هوية أو صلاحية مستقلة.
- الحفاظ على الفصل بين هوية الإنسان، الوصول، والحقيقة المالية.

هذه مواصفة سلوكية/دلالية. لا تحدد تقنية مصادقة، أو قاعدة بيانات، أو API، أو واجهة مستخدم، أو إطار عمل، أو مزوداً.

لا تمنح هذه المواصفة Authorization ولا تملك Financial Account.

## 2. REQ Coverage

| REQ | Primary | Supporting | Scope |
|---|---|---|---|
| REQ-FUNC-0001 | SPEC-0001 | — | فصل Person / Identifier / Access Account / Session ومنع خلط الهوية بوسيلة الوصول |
| REQ-FUNC-0002 | SPEC-0001 | SPEC-0007 | فصل Financial Account عن Identity / Access؛ الملكية المالية تبقى لدى Finance |
| REQ-FUNC-0004 | SPEC-0001 | — | تمييز Session كسياق وصول مؤقت عن الهوية المستمرة |

الحالة الدلالية لهذه المتطلبات لا تتجاوز ما حُسم في Stage 3–5؛ لا يعني وجودها هنا أنها أصبحت معتمدة بشرياً.

## 3. Primary / Supporting Ownership

**Primary:** SPEC-0001 يملك السلوك الأساسي للمتطلبات الثلاثة في نطاق الهوية والوصول والجلسة.

**Supporting:** SPEC-0007 يدعم REQ-FUNC-0002 فقط عندما يكون الحديث عن **Financial Account** وحدود الحقيقة المالية. هذا الدعم لا ينقل ملكية Financial Account إلى SPEC-0001.

- Identity يملك حقيقة Person وIdentifier.
- Access يملك حقيقة Access Account وAuthenticator وSession.
- Finance يملك حقيقة Financial Account.
- SPEC-0001 لا يقرر صلاحية الوصول؛ Authorization هو المالك الدلالي للقرار.
- SPEC-0001 لا يعرّف معنى Primary Account؛ DEC-0002 أصبح DECIDED / RESOLVED.

## 4. Concepts Used

المفاهيم المستخدمة هنا هي مفاهيم Stage 5 القائمة، دون إضافة Concepts أو Relationships جديدة:

- **Person:** الشخص/الجهة ذات الهوية المستمرة.
- **Identifier:** معرف أو إثبات مرجعي للشخص.
- **Access Account:** سياق الوصول للنظام.
- **Authenticator:** وسيلة إثبات حيازة للوصول.
- **Session:** سياق وصول مؤقت.
- **Financial Account:** إطار مالي يملكه Finance، ويظل مستقلاً عن Access Account.
- **Authorization:** قرار الصلاحية في سياق وغرض محدد؛ يستخدمه هذا المجال ولا يملكه.
- **Provenance:** وصف أصل/اشتقاق/إنتاج/تعديل المعلومة عند الحاجة.
- **Audit Record:** سجل رقابي للفعل أو الوصول أو القرار عند الحاجة.

لا تنشئ هذه المواصفة مفهوماً مستقلاً لـPassword أو Token أو Credential أو Device Identity؛ تفاصيل وسائل الإثبات والتنفيذ تبقى abstraction.

## 5. Preconditions

قبل إنشاء أو تغيير حالة مرتبطة بالوصول يجب أن يكون السياق الدلالي واضحاً:

1. إذا كان الفعل متعلقاً بالشخص، يكون Person هو المرجع المقصود.
2. إذا كان الفعل متعلقاً بالوصول، يكون Access Account هو المرجع المقصود.
3. إذا كان التحقق يعتمد على وسيلة إثبات، تكون العلاقة مع Authenticator واضحة.
4. إذا كان الطلب متعلقاً بسياق وصول مؤقت، يكون Session هو السياق المقصود.
5. لا يُفترض من وجود Access Account أن الشخص يملك Authorization.
6. لا يُفترض من وجود Access Account أن الشخص يملك Financial Account.
7. أي معنى قانوني أو ولائي غير محسوم لا يُستنتج من هذه المواصفة.

## 6. Core Behavior

السلوك الأساسي هو الحفاظ على سلسلة دلالية منفصلة:

**Person → Access Account → Authenticator / Session**

مع بقاء **Financial Account** خارج سلسلة الوصول وتحت ملكية Finance.

يجب أن يستطيع النظام التمييز بين:
- الشخص.
- معرفه.
- حساب الوصول الذي يمثل سياق دخوله.
- وسيلة الإثبات المستخدمة للوصول.
- الجلسة المؤقتة الحالية.
- الحساب المالي المستقل إن وجد.

وجود أكثر من Access Account أو Identifier لا يخلق Person جديداً لمجرد اختلاف سياق الوصول أو المعرف.

وجود Access Account لا يحول الحساب إلى Authorization، ولا يحول أي عنصر وصول إلى Financial Account.

## 7. Identity Lifecycle

### Person

يمثل Person هوية مستقرة عبر السياقات، ويمكن أن يمر دلالياً بحالات:
- إنشاء.
- نشط.
- غير نشط.
- تصحيح.

التصحيح لا يعني إنشاء Person جديد لمجرد تصحيح معلومة تخص الشخص.

لا يتكرر Person بسبب اختلاف النشاط أو Access Account أو Identifier أو انتهاء Session.

### Identifier

Identifier مرتبط بالشخص كمعرف/إثبات مرجعي، ويمكن أن يمر بحالات:
- إصدار.
- فعال.
- منتهي.
- مسحوب.

تعدد Identifiers لا يعني تعدد Persons، ولا يساوي Identifier عملية المصادقة نفسها.

## 8. Access Account Lifecycle

Access Account يمثل **حالة الوصول** وليس هوية الإنسان.

الحالات الدلالية الأساسية:
- إنشاء.
- فعال.
- موقوف.
- منتهٍ.
- استعادة عندما تكون الاستعادة مسموحة دلالياً.

الانتقال بين الحالات لا يغير Person الذي يرتبط به الحساب.

تعليق أو انتهاء Access Account لا يمحو Person ولا يغيّر الحقيقة المالية.

إغلاق أو انتهاء الوصول لا يعني تلقائياً إلغاء أي Financial Account أو Ledger أو Balance.

ولا تعني حالة Access Account الفعالة أن كل فعل داخل النظام مسموح؛ صلاحية الفعل يحددها Authorization ضمن سياقه.

## 9. Authenticator Relationship

Authenticator يمثل وسيلة إثبات حيازة مرتبطة بـAccess Account.

العلاقة الدلالية:

**Access Account → Authenticator**

والحالات الأساسية:
- enrolled.
- active.
- revoked.
- expired.

القواعد:
1. Authenticator لا يمثل Person.
2. Authenticator لا يصبح Authorization.
3. Authenticator لا يصبح Financial Account.
4. سحب أو انتهاء Authenticator لا يمحو Access Account.
5. وجود Authenticator فعال لا يعني أن كل فعل مسموح.
6. تفاصيل نوع وسيلة الإثبات، آلية التحقق، الأسرار، البروتوكول، أو التخزين ليست جزءاً من هذه المواصفة.

## 10. Session Lifecycle

Session هو سياق وصول مؤقت، وليس هوية مستقلة.

الحالات الأساسية:
- بدأ.
- فعال.
- منتهٍ.
- ملغى.

القواعد:
1. إنشاء Session لا ينشئ Person.
2. إنشاء Session لا ينشئ Access Account جديداً إذا كان الحساب نفسه قائماً.
3. انتهاء Session لا ينهي Person.
4. انتهاء Session لا ينهي Financial Account.
5. إلغاء Session يوقف سياق الجلسة، ولا يعيد تعريف الهوية.
6. Session لا تمنح Authorization من ذاتها.
7. أي صلاحية تستخدم أثناء Session تبقى خاضعة لقرار Authorization وسياقه.
8. لا تستمر الجلسة كحقيقة وصول لمجرد وجود أثر تاريخي لها.

## 11. Separation Rules

### Person ≠ Identifier ≠ Access Account ≠ Financial Account

| المفهوم | المعنى | المالك |
|---|---|---|
| Person | الشخص/الجهة ذات الهوية المستمرة | Identity |
| Identifier | معرف/إثبات مرجعي للشخص | Identity |
| Access Account | سياق حالة الوصول | Access |
| Financial Account | إطار الحقيقة المالية | Finance |

والفصل إلزامي:
- Person ليس Access Account.
- Identifier ليس Person.
- Identifier ليس Authenticator.
- Access Account ليس Financial Account.
- Financial Account ليس Access Account.
- Session ليس Person.
- Session ليس Access Account.
- Authorization ليست Access Account.
- Authorization ليست Financial Account.

ولا تسمح المواصفة باستنتاج دمج هذه المفاهيم من تشابه الاسم أو من استخدام واحد في سياق عملي.

## 12. قواعد ربط Person بالـAccess Account

يرتبط Access Account بشخص أو بسياق وصول مسموح وفق النموذج المفاهيمي القائم.

1. Person واحد قد يرتبط بأكثر من Access Account عندما يسمح السياق بذلك.
2. تعدد Access Accounts لا يخلق Persons متعددة.
3. Access Account لا يملك Person؛ Identity تظل مالكة حقيقة الشخص.
4. اختلاف النشاط أو الدور لا يستلزم إنشاء Person جديد.
5. Access Account لا يصبح Membership أو Role Assignment.
6. Role Assignment لا يتحول إلى Authorization لمجرد وجود Access Account.
7. لا يُستخدم Access Account كمرادف للحساب المالي.
8. أي علاقة مالية تظل ضمن حدود Finance.

## 13. قواعد الجلسة

- Session تشير إلى سياق وصول قائم بدلاً من أن تصبح بديلاً عنه.
- Session مؤقتة بطبيعتها ولها بداية ونهاية أو إلغاء.
- Session المنتهية لا تمثل وصولاً فعالاً.
- Session الملغاة لا تستمر كحالة وصول فعالة.
- Session لا تغير ملكية Person أو Access Account.
- Session لا تنشئ Authorization مستقلة.
- انتهاء Session لا يساوي حذف التاريخ.
- إذا احتاج فعل حساس إلى تتبع، يبقى أثره الرقابي منفصلاً عن Session نفسها.

## 14. حالات الرفض والمنع

يجب رفض أو منع الحالة الدلالية عندما تؤدي إلى خلط الحدود، ومن ذلك:
1. اعتبار Access Account هو Person.
2. اعتبار Identifier هو Person أو Authenticator.
3. اعتبار Financial Account امتداداً لـAccess.
4. منح Authorization لمجرد وجود Access Account.
5. اعتبار Session هوية مستمرة.
6. استخدام Session المنتهية أو الملغاة كسياق وصول فعال.
7. إسناد ملكية Financial Account إلى SPEC-0001.
8. استخدام انتهاء الوصول كدليل على انتهاء الحقيقة المالية.
9. استنتاج صلاحية مجالية من وجود دور أو حساب وصول دون قرار Authorization.
10. إدخال قاعدة قانونية أو ولائية غير محسومة على أنها سلوك ثابت.

## 15. الحالات والاستثناءات

### Person موجود، ولا يوجد Access Account فعال
حالة ممكنة؛ وجود Person لا يفرض وجود وصول فعال.

### Access Account موقوف
يبقى Person قائماً، بينما حالة الوصول غير فعالة وفق حدود Access.

### Authenticator منتهي أو مسحوب
لا يُعامل كوسيلة إثبات فعالة، ولا يؤدي ذلك بذاته إلى حذف Person.

### Session منتهية
تبقى الجلسة جزءاً من التاريخ الدلالي عند الحاجة، لكنها ليست سياق وصول فعالاً.

### Person لديه أكثر من Access Account
لا تنشأ هوية بشرية جديدة لكل حساب.

### Access Account موجود، ولا توجد Authorization
حالة صحيحة؛ الحساب يثبت سياق الوصول ولا يثبت الصلاحية على فعل مجالي.

### Financial Account موجود بصورة مستقلة
لا يغيّر ذلك تعريف Person أو Access Account، ولا ينقل ملكية Financial Account إلى Access.

### Primary Account غير محسوم
لا تُفرض علاقة أو تجميع جديد. **DEC-0002** أصبح DECIDED / RESOLVED.

## 16. History / Provenance / Audit Requirements

تتطلب التغييرات الحساسة قابلية التتبع دون إنشاء مفهوم جديد:
- تغييرات حالة Person أو Access Account أو Authenticator أو Session تكون قابلة للمراجعة عندما تكون حساسة أو خاضعة لمتطلب تدقيق.
- Provenance يصف أصل أو إنتاج أو تعديل المعلومة عند الحاجة، ولا يصبح مالكاً للهوية أو الوصول.
- Audit Record يسجل الفعل أو الوصول أو القرار لأغراض التدقيق، ولا يصبح Domain State.
- انتهاء Session لا يمحو أثرها التاريخي إذا كان الاحتفاظ بالأثر مطلوباً.
- تغييرات Authorization تبقى تحت ملكية Authorization؛ SPEC-0001 لا يصبح مالكاً لسجل الصلاحية.
- أي احتفاظ أو مدة قانونية غير محسومة لا تُخترع هنا.

## 17. Privacy / Sensitivity Considerations

Person وIdentifier وAccess Account وAuthenticator وSession بيانات حساسة بدرجات مختلفة وفق تصنيف Stage 5.

1. لا تُعامل بيانات الهوية والوصول كبيانات عامة افتراضياً.
2. الوصول إلى بيانات الشخص يكون ضمن السياق المصرح به.
3. وجود Access Account لا يبرر كشف بيانات Person خارج الغرض المسموح.
4. Authenticator قد يكون شديد الحساسية، ولا يغيّر ذلك ملكية Access للحساب.
5. Session قد تحمل سياق وصول حساس، ولا تصبح مصدراً مستقلاً لحقيقة الهوية.
6. لا تُفرض تصنيفات قانونية عالمية؛ الولاية والسياسة المحلية قد تؤثر وفق القرارات المفتوحة.
7. Privacy لا تُحوّل إلى Authorization داخل SPEC-0001؛ القرار السلطوي يبقى لدى Authorization.

## 18. Offline Boundaries

هذه المواصفة لا تجعل الهوية أو الوصول أو الجلسة نهائية لمجرد أن الحالة موجودة محلياً.

- Offline Operation ≠ Finality.
- وجود حالة محلية لا ينقل Source of Truth من Identity أو Access.
- Device أو Pending Operation لا يملكان حقيقة Person أو Access Account.
- العملية المحلية المتعلقة بالوصول لا تصبح حقيقة نهائية لمجرد حفظها محلياً.
- عند وجود تعارض، لا تحدد هذه المواصفة خوارزمية حسم أو مزامنة.
- DEC-0013 والقرارات المتعلقة بفقدان الجهاز والعمليات المعلقة تبقى ضمن حدودها الDECIDED / RESOLVED.
- لا يترتب على offline إنشاء Concept جديد أو نقل الملكية.

## 19. Agent Boundaries

Agent لا يملك Domain Truth لمجرد كونه Agent.

1. Agent قد يطلب أو ينفذ فعلاً إذا كانت السلطة المقررة تسمح بذلك.
2. Agent لا ينشئ Person Truth مستقلة.
3. Agent لا يملك Access Account أو Financial Account تلقائياً.
4. Agent لا ينشئ Authorization من ذاته.
5. Agent Action يبقى فعلاً منفصلاً عن الحقيقة الدومينية التي قد يتأثر بها.
6. حدود الأفعال التي يستطيع Agent تنفيذها تعتمد على Authorization / Authority Policy والقرارات المفتوحة ذات الصلة.
7. DEC-0006 وDEC-0007 لا يُفترض منهما قرار تفصيلي داخل هذه المواصفة.

## 22. Acceptance Criteria

تُعد SPEC-0001 مستوفية على المستوى الدلالي عندما يمكن إثبات الآتي:
1. يمكن التمييز في كل حالة بين Person وIdentifier وAccess Account وFinancial Account.
2. يمكن تمثيل Person دون إنشاء Access Account بالضرورة.
3. يمكن تمثيل Access Account دون اعتباره Person.
4. يمكن تمثيل أكثر من Identifier للشخص دون إنشاء Persons إضافية.
5. يمكن تمثيل Authenticator مرتبطاً بـAccess Account دون اعتباره Person.
6. يمكن إنشاء Session كسياق مؤقت دون إنشاء هوية جديدة.
7. انتهاء Session يجعلها غير فعالة دون إنهاء Person.
8. تعليق أو انتهاء Access Account لا يغير حقيقة Person.
9. لا يُستنتج Authorization من وجود Access Account وحده.
10. لا تنتقل ملكية Financial Account إلى SPEC-0001.
11. REQ-FUNC-0002 يحتفظ بـSPEC-0007 كـSupporting فقط فيما يخص Financial Account.
12. لا تستخدم المواصفة قرار DEC-0002 كقرار محسوم.
13. الحالات الحساسة قابلة للتتبع عبر Provenance/Audit حيث يلزم، دون تحويلهما إلى Domain Truth.
14. الحدود Offline وAgent لا تنشئ ملكية أو Concepts جديدة.
15. لا تتطلب أي قاعدة قبول تقنية محددة لتنفيذها.

## 24. Open Decisions / Dependencies

### DEC-0002 — Primary Account
يبقى مفتوحاً.

### DEC-0001 — الولاية / السوق
