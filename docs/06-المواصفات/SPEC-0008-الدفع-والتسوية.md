# SPEC-0008 — الدفع والتسوية

## 1. الغرض والنطاق
تحدد هذه المواصفة السلوك الدلالي لـPayment وSettlement وحدودهما مع Financial Transaction وLedger Entry وObligation وInvoice.
القاعدة:
**Payment ≠ Settlement ≠ Financial Transaction ≠ Ledger Entry**.
Payments/Settlement لا تملك Financial Truth؛ الاعتراف المالي والدفتر يبقيان لدى Finance.
لا تحدد هذه المواصفة مزود دفع أو API أو تنفيذاً أو تقنية.

## 5. Payment
Payment هي عملية تقديم قيمة أو محاولة تقديمها لتلبية التزام/مطالبة/غرض مالي.
هي ليست Settlement ولا Financial Transaction بالضرورة ولا Ledger Entry.

### 5.1 lifecycle
دلالياً يمكن أن تمر:
**initiated → authorized/accepted → pending → completed**
أو:
**initiated → rejected/failed/cancelled**
وقد يحدث **reversed** بعد أثر سابق ذي معنى.
لا تفرض كل الحالات في كل سياق.

### 5.2 معنى الحالات
- initiated: بدأت محاولة الدفع.
- pending: لم تصل إلى حالة محسومة.
- accepted/completed: حالة معالجة دفع بحسب السياق، ولا تعني بالضرورة Settlement.
- rejected/failed: لم يكتمل الدفع المطلوب.
- cancelled: أوقف قبل الاكتمال حيث يسمح السياق.
- reversed: عكس أثر سابق؛ لا يمحو التاريخ.

## 6. Settlement
Settlement هي حسم/تخصيص/إتمام مالي للالتزام أو القيمة وفق سياق المجال.
هي ليست Payment ولا Ledger Entry.
يمكن أن تمر:
**pending → matched → settled**
مع **reversed/disputed** عند انطباق المعنى.

حالة Settlement لا تنقل ملكية Financial Account أو Ledger.

## 7. Financial Transaction وLedger boundary
Financial Transaction هي الحقيقة الدومينية للواقعة المالية وتملكها Finance.
Ledger Entry هو الأثر المالي المعترف به ويملكه Finance.
Payment وSettlement قد تكونان مصادر أو مدخلات لعملية الاعتراف، لكنهما لا تصبحان Finance Truth لمجرد اكتمال المعالجة.

## 8. Obligation / Invoice
Payment قد ترتبط بـObligation أو Invoice.
Settlement قد ترتبط بالالتزام الذي تعالجه.
Invoice تبقى Commerce truth، وObligation تبقى Financial Relations truth.
لا تساوي المواصفة Payment بـInvoice أو Obligation.

## 9. الحالات الأساسية
### دفع ناجح دون تسوية
Payment قد تصبح completed بينما Settlement لا تزال pending.
النتيجة: لا نساوي المرحلتين.
### دفع معلق
Pending Payment لا تعني satisfaction ولا Ledger finality.
### دفع مرفوض
Rejected/failed Payment لا تسقط Obligation تلقائياً.
### دفع جزئي
يمكن أن تعالج Payment جزءاً من Obligation، ويبقى الجزء غير المسدد ضمن Financial Relations.
### تسوية ناجحة
Settled تعني تحقق معنى التسوية في سياق Payments/Settlement، وإذا نشأ أثر مالي معترف به فهو لدى Finance.
### تسوية فاشلة
Settlement failure لا يمحو Payment history ولا يخلق Ledger truth تلقائياً.

## 10. التكرار
يمكن أن توجد محاولات دفع متعددة لنفس الغرض دون افتراض أنها Payment واحدة.
كشف التكرار كسياسة تنفيذية أو خوارزمية خارج نطاق هذه المواصفة.
عند الاشتباه في تكرار:
- لا تدمج الوقائع بلا أساس.
- لا تحذف المحاولة التاريخية.
- لا تنشئ Financial Transaction أو Ledger Entry مصطنعاً.
REQ-0062 والتفاصيل العابرة للمجالات تقع في SPEC-0023، وليس هنا.

## 11. الإلغاء
إلغاء Payment قبل اكتمالها يغير حالتها وفق السياق ولا يمحو التاريخ.
إلغاء/إبطال Settlement لا يعني حذف Payment.
لا تضع هذه المواصفة قاعدة قانونية عامة للإلغاء.

## 12. الاسترداد/العكس
يمكن وصف refund/reversal كحد دلالي لتغيير نتيجة سابقة، دون إنشاء Refund Concept.
العكس لا يساوي حذف السابق.
الأثر المالي الناتج عن reversal/correction يبقى ضمن Finance وفق قواعده.
تفاصيل الإرجاع والاسترداد العابرة للمجالات ضمن SPEC-0023.

## 13. Financial Recognition
عندما ينتج عن Payment/Settlement أثر مالي معترف به:
- Finance يملك Financial Transaction.
- Finance يملك Ledger Entry.
- Balance يظل مشتقاً.
Payments/Settlement لا تملك هذه الحقائق.
"completed" أو "settled" وحدهما لا يفرضان Ledger finality في كل سياق.

## 14. Failure / Exception boundaries
- Payment failed ≠ Obligation satisfied.
- Payment pending ≠ Payment settled.
- Settlement failed ≠ Payment deleted.
- Settlement reversed ≠ history deleted.
- Offline Payment ≠ final financial recognition.
- Device ≠ Source of Truth.
- Conflict ≠ new financial truth.

## 15. History / Provenance / Audit
يحفظ تاريخ Payment وSettlement وحالاتهما ذات المعنى.
Provenance يصف المصدر/الاشتقاق.
Audit Record يسجل الفعل أو القرار.
Correction/Reversal لا يمحو التاريخ.
لا Event Sourcing أو تقنية مماثلة مفروضة.

## 16. Privacy / Authorization
Payment/Settlement أفعال مالية حساسة.
تنفيذها يتطلب السلطة المناسبة ضمن Authorization.
Role أو Channel أو Agent لا ينشئ السلطة بذاته.
Agent لا يتجاوز Authorization.

## 17. Offline / Agent
**Offline ≠ Finality**.
Pending Operation لا تصبح Payment/Settlement نهائية لمجرد وجودها على Device.
Agent قد ينفذ Payment/Settlement فقط ضمن Authority/Authorization، ولا يصبح Domain Owner.
لا تحدد هذه المواصفة sync/conflict algorithm.

## 18. Source of Truth
| الحقيقة | المالك |

| Settlement | Payments/Settlement |
| Financial Transaction | Finance |
| Ledger Entry | Finance |

| Invoice | Commerce |
