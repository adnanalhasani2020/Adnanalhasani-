# SPEC-0003 — الوصول السياقي والسلطة

## 1. Purpose / Scope

تحدد هذه المواصفة السلوك الدلالي لمجال **Authorization** فيما يتعلق بتحديد متى يكون الفعل أو الوصول مسموحاً ضمن سياق محدد، ولأي غرض، وتحت أي حدود.

النطاق يشمل:
- **Authorization** كقرار صلاحية سياقي.
- **Authorization Grant** كمنحة سلطة محددة.
- **Authority Policy** كقاعدة/سياسة يقيّم ضمنها السماح.
- سياق الوصول.
- الغرض من الوصول.
- نطاق الصلاحية وحدوده.
- العلاقة بين Membership وRole Assignment وبين Authorization.
- العلاقة بين Family Relationship وDelegation وAuthorization.
- تقليل نطاق الوصول وفق الغرض والحاجة والحساسية.
- انتهاء الصلاحية والإلغاء والتعليق.
- الحدود الدلالية للصحة والمال والخصوصية والوكلاء والعمل دون اتصال.

هذه مواصفة سلوكية/دلالية وليست مواصفة تنفيذية. لا تحدد DB أو SQL أو API أو UI أو Framework أو Provider أو آلية مزامنة أو خوارزمية حسم تعارض.

المبدأ المركزي:

**Role Assignment يصف الدور السياقي؛ Authorization يقرر ما الذي يجوز فعله أو الوصول إليه في سياق وغرض وحدود محددة.**

وجود Person أو Access Account أو Membership أو Role Assignment أو Family Relationship أو Delegation لا يكفي وحده لإثبات Authorization.

لا تنقل هذه المواصفة ملكية Domain Truth إلى Authorization. Authorization تملك **قرار الصلاحية**، بينما يبقى Domain Truth لدى مجاله الأصلي.

## 3. Primary / Supporting Ownership

### Primary

SPEC-0003 يملك السلوك الأساسي لـ:
- REQ-FUNC-0009.
- REQ-FUNC-0010.

ويملك قرار Authorization الدلالي عندما يكون المطلوب تحديد ما يجوز فعله أو الوصول إليه في سياق وغرض ونطاق محدد.

### Supporting

SPEC-0003 يدعم:
- REQ-FUNC-0005 وREQ-FUNC-0006 عبر Authorization عندما تكون العلاقة الأسرية أو حدود الطفل مدخلاً لسياق الصلاحية؛ Primary تبقى SPEC-0004.
- REQ-SEC-0049 وREQ-SEC-0052 عبر القرار السياقي وتقليل النطاق؛ Primary تبقى SPEC-0022.
- لا يغيّر SPEC-0003 ملكية REQ-FUNC-0028 أو REQ-NFR-0055.

### حدود الدعم

الدعم لا يعني:
- نقل Primary ownership.
- امتلاك Family Relationship.
- امتلاك Delegation.
- امتلاك Health Record أو Financial Account.
- امتلاك Activity أو Membership أو Role Assignment.
- امتلاك Agent.

## 4. Concepts Used

المفاهيم المستخدمة هنا هي مفاهيم Stage 5 القائمة فقط:

- **Person:** الهوية البشرية؛ الحقيقة الأساسية لدى Identity.
- **Access Account:** سياق الوصول؛ ملكيته لدى Access.
- **Activity:** سياق النشاط؛ ملكيته لدى Activities.
- **Membership:** علاقة Person بالنشاط؛ ملكيتها الدومينية لدى Activities.
- **Role Assignment:** الدور المسند داخل سياق؛ ملكيته الدومينية لدى Activities.
- **Family Relationship:** العلاقة الأسرية؛ ملكيتها لدى Family.
- **Delegation:** علاقة/سياق تفويض؛ لا تساوي Authorization Grant.
- **Authorization Grant:** منحة سلطة سياقية؛ تملك Authorization حقيقة المنحة.
- **Agent:** وكيل يمكن أن يعمل ضمن سلطة مقررة، لكنه ليس Authorization.
- **Authority Policy:** سياسة/قاعدة السلطة التي يقيّم ضمنها السماح.
- **Provenance:** وصف أصل أو اشتقاق أو تعديل المعلومة.
- **Audit Record:** سجل رقابي للفعل أو القرار.
- **Device:** سياق جهاز؛ لا يملك Domain Truth.
- **Pending Operation:** عملية محلية معلقة؛ لا تملك Authorization النهائية.
- **Conflict:** تعارض تشغيلي؛ لا يملك Domain Truth.
- **State Record:** أداة نمذجة وصفية للحالة وليست بديلاً عن المفهوم الدوميني.

لا تنشئ هذه المواصفة Concepts باسم:
- Permission.
- Resource.
- Access Rule.
- Policy Rule.
- Access Control List.
- Capability.
- Role Permission.

هذه ألفاظ وصفية عند الحاجة فقط، وليست مفاهيم Stage 5 مستقلة.

## 5. Preconditions

قبل تقييم أو تفسير Authorization:

1. يجب تحديد الفاعل المقصود ضمن المفاهيم القائمة، دون إنشاء Actor جديد.
2. يجب أن يكون سياق الوصول مفهوماً؛ Access Account قد يكون جزءاً من السياق لكنه ليس Authorization.
3. يجب أن يكون Activity أو المجال المقصود واضحاً عندما تكون الصلاحية سياقية له.
4. إذا استند التقييم إلى دور، يجب أن تكون Membership وRole Assignment ذات الصلة واضحة.
5. إذا استند إلى علاقة أسرية، يجب أن تكون Family Relationship وDelegation، إن وجدت، ضمن معناهما القائم.
6. يجب تحديد الغرض والسياق والنطاق بالقدر الدلالي اللازم لتقييد القرار.
7. لا يكفي وجود Role Assignment وحده.
8. لا تكفي Family Relationship وحدها.
9. لا تكفي Delegation وحدها لإثبات Authorization Grant.
10. لا يكفي Access Account وحده.
11. لا يكفي كون الفاعل Agent.
12. لا تنقل Authorization ملكية الحقيقة التي سيؤثر فيها الفعل.
13. لا تُستنتج قاعدة قانونية غير محسومة من DEC-0001 أو DEC-0004.

## 6. Authorization Context

Authorization هي قرار صلاحية مرتبط بسياق محدد.

السياق يجيب عن الأسئلة الدلالية الأساسية:
- من هو الفاعل أو صاحب الطلب ضمن الهوية/الوصول القائم؟
- ما المجال أو Activity أو العلاقة ذات الصلة؟
- ما الفعل أو نوع الوصول المطلوب؟
- ما الغرض المسموح؟
- ما النطاق الذي يغطيه القرار؟
- ما القيود الزمنية أو السياقية ذات الصلة؟

### قواعد السياق

1. Authorization لا تُقرأ خارج سياقها كصلاحية عامة.
2. سياق Activity لا يجعل كل أفعال الشخص مسموحة.
3. Membership لا تصبح Authorization.
4. Role Assignment لا يصبح Authorization.
5. Access Account لا يصبح Authorization.
6. Family Relationship لا تصبح Authorization.
7. Delegation لا تصبح Authorization Grant تلقائياً.
8. Agent لا يصبح Authorization.
9. Authorization لا تنقل ملكية Domain Truth.

### Person / Access Account

SPEC-0001 يثبت:
**Person ≠ Access Account.**

لذلك:
- Person هو الهوية.
- Access Account هو سياق الوصول.
- Authorization تقرر الصلاحية ضمن سياقها.
- وجود Access Account لا يثبت أن كل فعل مسموح.

## 7. Authority Policy

**Authority Policy** هي القاعدة أو السياسة التي يقيّم ضمنها السماح.

هي ليست Authorization Grant.

التمييز:

| المفهوم | السؤال |
|---|---|
| Authority Policy | وفق أي قاعدة/سياسة يتم تقييم السماح؟ |
| Authorization Grant | ما المنحة السلطوية المحددة الموجودة في السياق؟ |
| Role Assignment | ما الدور المسند للشخص داخل النشاط؟ |
| Membership | ما علاقة الشخص بالنشاط؟ |

### قواعد Authority Policy

1. Authority Policy لا تصبح Grant.
2. Grant لا تصبح Policy.
3. Role Assignment قد يدخل كمدخل للتقييم وفق السياسة.
4. Family Relationship أو Delegation قد تدخل كمدخل للسياق عندما يكون ذلك مسموحاً.
5. السياسة لا تنقل ملكية Domain Truth.
6. لا تُعرّف هذه المواصفة Permission أو ACL أو Capability كمفاهيم.
7. لا تُحسم هنا القواعد القانونية الخاصة بالعمر أو الولاية أو القطاع.
8. DEC-0001 وDEC-0004 يبقيان مفتوحين.

### Agent

Authority Policy قد تحدد حدود السلطة المقررة للوكيل، لكن:
- Agent ليس Authority Policy.
- Agent ليس Authorization.
- وجود Agent لا ينشئ Policy أو Grant تلقائياً.

## 8. Authorization Grant

**Authorization Grant** تمثل منحة سلطة سياقية.

يجب أن تكون قابلة للفهم من خلال:
- صاحب/موضوع المنحة ضمن المفاهيم القائمة.
- الفعل أو نوع الوصول المقصود.
- السياق.
- الغرض.
- النطاق.
- فترة الصلاحية عندما يكون الزمن جزءاً من معناها.
- حالة المنحة، مثل active أو revoked أو expired، وفق النموذج القائم.

هذه ليست إضافة Attributes تقنية أو نموذج بيانات جديد؛ هي وصف للسلوك الدلالي للمفهوم القائم.

### Grant ≠ Family Relationship

Grant ليست Family Relationship.

### Grant ≠ Delegation

Delegation قد تكون أساساً أو سياقاً لتقييم Grant، لكنها ليست Grant نفسها.

### Grant ≠ Role Assignment

Role Assignment قد يكون أساساً لتقييم Grant، لكنه لا يصبح Grant.

### Grant ≠ Domain Ownership

Grant تمنح سلطة محددة ولا تنقل ملكية:
- Financial Account.
- Ledger Entry.
- Balance.
- Clinical Record.
- Patient Context.
- Activity.
- Membership.

## 9. Role Assignment → Authorization Boundary

Role Assignment يجيب:

> **ما الدور المسند للشخص داخل Activity؟**

Authorization تجيب:

> **ما الفعل أو الوصول المسموح به، لمن، في أي سياق، لأي غرض، وتحت أي حدود؟**

لذلك:

1. Role Assignment قد يكون مدخلاً لتقييم Authorization.
2. Role Assignment لا يقرر Authorization.
3. Role Assignment لا يمنح صلاحية مطلقة.
4. اسم الدور لا يحدد وحده النطاق.
5. Manager لا يحصل تلقائياً على كل بيانات Activity.
6. Employee لا يستطيع فعلاً خارج نطاق السلطة المقررة لمجرد كونه Employee.
7. Owner لا يصبح تلقائياً مالكاً لكل الحقيقة المالية.
8. Doctor لا يحصل تلقائياً على كل البيانات الصحية لمجرد اسم الدور.
9. Teacher لا يحصل تلقائياً على كل بيانات الطلاب.
10. Parent لا يحصل تلقائياً على كل بيانات الطفل.
11. تغيير Role Assignment لا يعني الاحتفاظ بكل Authorization السابقة.
12. انتهاء Role Assignment قد يؤثر في صلاحيات مستقبلية وفق Authorization policy، دون إعادة تعريف Person.

**مرجع SPEC-0002:** Membership وRole Assignment سياق ودور، لا قرار صلاحية.

## 10. Family Relationship → Delegation → Authorization Boundary

الفصل الثلاثي إلزامي:

**Family Relationship ≠ Delegation ≠ Authorization Grant**

### Family Relationship

تصف العلاقة الأسرية بين الأشخاص وفق مفهوم Stage 5.

وجودها وحده لا يمنح وصولاً إلى:
- Health.
- Education.
- Finance.
- Communication.
- Access Accounts.

### Delegation

Delegation تصف علاقة/سياق تفويض.

وجود Delegation لا يعني:
- صلاحية غير محدودة.
- Grant عالمية.
- نقل ملكية Domain Truth.
- صلاحية في كل المجالات.

### Authorization Grant

هي المنحة السلطوية المحددة التي تُستخدم لإثبات أن فعلاً أو وصولاً معيناً مسموح ضمن سياقه.

### النتيجة

1. Family Relationship يمكن أن تكون أساساً لسياق تفويض.
2. Delegation يمكن أن تكون أساساً لتقييم Authorization.
3. Authorization Grant يجب أن تظل محددة بالسياق والغرض والنطاق.
4. لا توجد قاعدة عامة تجعل Family Relationship → Delegation → Authorization سلسلة إلزامية.
5. DEC-0004 أصبح DECIDED / RESOLVED.

## 11. Purpose / Context Limitation

الغرض ليس Concept جديداً؛ هو قيد دلالي في تفسير Authorization.

يجب أن يكون الوصول:
- مرتبطاً بالسياق المناسب.
- مرتبطاً بالغرض المسموح.
- غير أوسع من الحاجة.
- خاضعاً للحساسية والقيود ذات الصلة.
- قابلاً للإلغاء أو الانتهاء عندما يكون ذلك جزءاً من القرار.

### مثال دلالي

وجود Role Assignment كـManager داخل Activity لا يعني أن الشخص يستطيع قراءة كل بيانات الأشخاص لكل غرض.

وجود Family Relationship لا يعني أن الشخص يستطيع قراءة Clinical Record لكل غرض.

وجود Authorization Grant لغرض محدد لا يوسعها تلقائياً إلى أغراض أخرى.

### Purpose Limitation

1. لا تستخدم Grant لغرض غير الغرض الذي منحت من أجله عندما يكون الغرض قيداً في القرار.
2. لا توسع السياق لمجرد سهولة الاستخدام.
3. لا تحول صلاحية في Activity إلى صلاحية عالمية.
4. لا تجعل Family Relationship بديلاً عن تحديد الغرض.
5. لا تجعل Role Assignment بديلاً عن تحديد الغرض.

## 12. Least-Privilege Semantics

**Least privilege** هنا مبدأ دلالي: منح أقل نطاق لازم لتحقيق الغرض المسموح، دون افتراض Taxonomy قانونية جديدة.

يعني ذلك:

1. لا تمنح صلاحية أوسع من المطلوب.
2. لا تجعل الدور مصدراً لصلاحيات غير محددة.
3. لا تجعل Agent يحصل على وصول أوسع من الحاجة إلى تنفيذ الفعل المصرح به.
4. لا تجعل Family Relationship مصدراً لوصول شامل.
5. لا تجعل Membership مصدراً لصلاحية شاملة.
6. لا تجعل Access Account مصدراً لصلاحية مجالية.
7. إذا كان النطاق محدوداً، فلا يتوسع لمجرد وجود Grant.
8. إذا انتهى القيد الزمني، لا تبقى Grant فعالة بسبب وجودها التاريخي.
9. لا تنشئ هذه المواصفة تصنيفاً قانونياً جديداً لمستويات الصلاحية.

## 13. Scope Limitation

نطاق Authorization قد يتقيد بـ:
- Activity.
- علاقة Person بالنشاط.
- دور محدد.
- غرض.
- فعل محدد.
- مجال أو سياق حساس.
- فترة زمنية.
- قيود أخرى مثبتة في القرار.

هذه ليست Concepts جديدة.

### قواعد النطاق

1. Grant داخل Activity لا تصبح Grant في Activity أخرى.
2. Grant لغرض معين لا تصبح Grant لكل الأغراض.
3. Grant لبيانات معينة لا تصبح وصولاً شاملاً لكل بيانات المجال.
4. Grant مؤقتة لا تصبح دائمة.
5. Grant ملغاة لا تستخدم كصلاحية فعالة.
6. Grant منتهية لا تستخدم كصلاحية فعالة.
7. Role Assignment في Activity A لا ينقل Authorization تلقائياً إلى Activity B.
8. Family Relationship لا توسع النطاق خارج القرار.
9. Delegation لا توسع نفسها إلى كل المجالات.
10. Authorization لا تنقل Domain Ownership.

## 14. Grant Lifecycle

الدورة الدلالية للـAuthorization Grant تشمل، بحسب ما ينطبق:
- إنشاء/منح.
- فعالة.
- تعليق.
- إلغاء.
- انتهاء.

### Grant فعالة

Grant الفعالة لا تزال صالحة ضمن سياقها وغرضها ونطاقها وشروطها.

### Grant معلقة

Grant المعلقة لا تُستخدم كصلاحية فعالة خلال التعليق.

### Grant ملغاة

Revoked Grant لا تعود فعالة لمجرد وجودها في التاريخ.

الإلغاء لا يمحو حقيقة أن Grant كانت موجودة أو أن قراراً صدر، إذا كان الاحتفاظ بالتاريخ مطلوباً.

### Grant منتهية

Expired Grant لا تُستخدم كصلاحية فعالة بعد انتهاء مدتها.

الانتهاء لا يمحو التاريخ.

### التغيير

تغيير شروط الصلاحية لا يعني إعادة تعريف Person.

تغيير Role Assignment لا يعيد إنشاء Person.

تغيير Membership لا يمحو تاريخ Authorization السابقة.

## 15. Membership / Role Changes and Authorization

عند حدوث تغيير في Membership أو Role Assignment:

1. Person يبقى نفسه.
2. Activity تبقى نفسها ما لم تتغير لسبب مستقل.
3. Membership تظل حقيقة العلاقة.
4. Role Assignment تظل حقيقة الدور.
5. Authorization تعيد تقييم ما إذا كانت الصلاحية المستقبلية لا تزال قائمة، ضمن سياق Authorization.
6. لا يُفترض الاحتفاظ تلقائياً بكل Grant السابقة.
7. لا يُفترض الإلغاء القانوني الشامل دون قرار مناسب.
8. لا تُخلق Authorization جديدة من مجرد تغيير الدور.
9. لا تُنقل صلاحية من Activity إلى Activity أخرى تلقائياً.
10. التاريخ يبقى قابلاً للتتبع.

### انتهاء Membership

انتهاء Membership قد يؤثر في الصلاحيات التابعة لذلك السياق، لأن السياق الأساسي لم يعد فعالاً.

لكن:
- لا ينتهي Person.
- لا تُمحى Role Assignments التاريخية.
- لا تُمحى Grant التاريخية.
- لا تنشأ هوية جديدة.

## 16. حالات الرفض والمنع

يجب رفض أو منع الحالة الدلالية عندما يحدث أحد الآتي:

1. استخدام Role Assignment كبديل عن Authorization.
2. منح Manager وصولاً مطلقاً لمجرد الاسم.
3. منح Employee وصولاً خارج دوره لمجرد كونه موظفاً.
4. منح Owner كل البيانات لمجرد وصفه Owner.
5. منح Parent وصولاً صحياً لمجرد Family Relationship.
6. منح Parent وصولاً تعليمياً شاملاً لمجرد القرابة.
7. منح وصول مالي لمجرد الدور.
8. استخدام Delegation كـAuthorization Grant دون منحة/قرار سلطوي مناسب.
9. استخدام Family Relationship كصلاحية مباشرة.
10. استخدام Authority Policy كأنها Grant قائمة.
11. استخدام Access Account كأنها Authorization.
12. استخدام Agent كأن وجوده يمنحه Authorization.
13. جعل Agent يمنح نفسه Authorization.
14. استخدام Grant منتهية كصلاحية فعالة.
15. استخدام Grant ملغاة كصلاحية فعالة.
16. توسيع Grant خارج نطاقها.
17. استخدام Grant لغرض غير الغرض المسموح عندما يكون الغرض قيداً في القرار.
18. نقل Authorization إلى Domain Ownership.
19. استخدام Authorization لتعديل Financial Account أو Ledger Entry أو Balance خارج السلطة المناسبة وفي المجال المالك.
20. استخدام Authorization للوصول إلى Clinical Record بلا قرار صحي مناسب.
21. اعتبار Audit Record مصدر الحقيقة.
22. اعتبار Provenance Authorization.
23. اعتبار Offline Grant نهائية لمجرد وجودها محلياً.
24. استنتاج قاعدة قانونية ثابتة من DEC-0001 أو DEC-0004.
25. إنشاء Concept جديد لتغطية أي حالة من هذه الحالات.

## 17. Privacy / Sensitivity Boundary

الخصوصية هنا قيد دلالي على الوصول، وليست Conceptاً جديداً.

REQ-SEC-0049 وREQ-SEC-0052 وREQ-NFR-0055 تضع حدوداً مهمة:
- الوصول يكون بالسياق والصلاحية والغرض.
- لا يُمنح الدور أو الوكيل وصولاً أوسع من الحاجة والغرض.
- الخصوصية تعتمد على تقليل الوصول والاستخدام المقيد بالسياق والغرض.

### الحساسية

تختلف حساسية Domain Truth باختلاف المجال، ومن أمثلتها:
- Clinical Record.
- Patient Context.
- Prescription.
- Financial Account.
- بيانات الأشخاص.

لا تنشئ هذه المواصفة Taxonomy قانونية جديدة للحساسية.

### قواعد الخصوصية

1. الحساسية سبب لتضييق السياق، وليست سبباً لإنشاء Concept جديد.
2. Family Relationship لا تتجاوز الحساسية الصحية أو المالية أو التعليمية.
3. Role Assignment لا تتجاوز الحساسية.
4. Agent لا يتجاوز الحساسية لمجرد كونه وكيلاً.
5. Grant يجب أن تظل ضمن النطاق والغرض.
6. الإلغاء والانتهاء يوقفان الاستخدام المستقبلي وفق القرار.
7. Audit يوثق الفعل ولا يملك البيانات الأصلية.
8. Provenance يصف الأصل ولا يمنح وصولاً.

## 18. Health Boundary

الصحة مجال مستقل يملك حقائقه.

هذه المواصفة لا تمنح صلاحية صحية نهائية.

### Patient Context

Patient Context يظل ضمن المجال الصحي.

### Clinical Record

Clinical Record يظل Domain Truth صحياً.

### Prescription

Prescription تظل Domain Truth صحية وفق مالكها.

### قواعد الوصول

1. Family Relationship لا تعني تلقائياً الوصول إلى Clinical Record.
2. Parent لا يحصل تلقائياً على كل بيانات الطفل الصحية.
3. Role Assignment كـDoctor لا يعني تلقائياً كل وصول صحي ممكن.
4. أي وصول صحي يحتاج Authorization مناسبة للسياق والغرض والنطاق.
5. Authorization لا تصبح Clinical Record.
6. Authorization لا تملك Patient Context.
7. Authorization لا تنقل ملكية الحقيقة الصحية.

DEC-0004 وDEC-0001 يبقيان مفتوحين حيث تؤثر قواعد الأسرة أو الولاية.

## 19. Finance Boundary

Authorization لا تملك Financial Account.

كما لا تملك:
- Ledger Entry.
- Balance.
- Financial Transaction.

### قواعد

1. الدور لا يثبت ملكية الحساب المالي.
2. Manager لا يملك تلقائياً الحقيقة المالية.
3. Owner كدور نشاط لا يثبت قانونياً ملكية Financial Account.
4. Authorization قد تسمح بفعل مالي محدد ضمن سياق مناسب، لكنها لا تنقل Domain Ownership.
5. Access Account لا تصبح Financial Account.
6. Audit Record لا يصبح Ledger Entry.
7. Provenance لا يصبح Financial Truth.
8. أي حسم للملكية المالية يبقى ضمن Finance وبالقرارات المناسبة.

## 20. History / Provenance / Audit

يجب إبقاء المفاهيم التالية منفصلة:

| المفهوم | المعنى | ما ليس هو |
|---|---|---|
| Authorization Decision | قرار الصلاحية | ليس Domain Truth الذي يؤثر فيه |
| Authorization Grant | منحة سلطة محددة | ليست Family Relationship أو Delegation |
| Audit Record | سجل رقابي للفعل/القرار | ليس Source of Truth |
| Provenance | أصل/اشتقاق/تعديل المعلومة | ليس Authorization |
| Domain Truth | الحقيقة التي يملكها المجال | ليست Audit أو Provenance |

### قواعد التاريخ

1. Grant الملغاة تبقى قابلة للتتبع إذا كان الاحتفاظ بالتاريخ مطلوباً.
2. Grant المنتهية لا تصبح فعالة بسبب وجودها التاريخي.
3. تغيير Role Assignment لا يمحو تاريخ Grant.
4. انتهاء Membership لا يمحو تاريخ Authorization.
5. Audit يوثق القرار أو الفعل دون أن يصبح القرار نفسه.
6. Provenance يصف أصل القرار أو المعلومة دون أن يمنح سلطة.
7. لا تُفرض مدة احتفاظ قانونية غير محسومة.

## 21. Offline Boundaries

**Offline Operation ≠ Authorization Finality.**

الحالة المحلية لا تنقل Source of Truth.

### Device

Device لا يملك Authorization النهائية.

### Pending Operation

Pending Operation قد تحمل طلباً أو محاولة تغيير، لكنها لا تصبح Grant نهائية لمجرد وجودها محلياً.

### Conflict

Conflict لا يقرر الصلاحية ولا يملك Domain Truth.

### القواعد

1. Offline Grant/decision لا تصبح نهائية تلقائياً.
2. وجود Grant محلية لا يثبت أن المجال المالك قبلها نهائياً.
3. Pending Operation ليست Authorization Grant.
4. Conflict ليس Authorization.
5. Device ليس Authorization.
6. لا تحدد هذه المواصفة Sync algorithm.
7. لا تحدد خوارزمية Conflict Resolution.
8. الحسم النهائي يبقى ضمن المجال المالك والحكم الدلالي المناسب.
9. الحساسية الصحية والمالية لا تخفض هذه الحدود بسبب العمل دون اتصال.

## 22. Agent Boundaries

**Agent ≠ Authorization.**

**Agent Action ≠ Authorization.**

Agent قد يعمل فقط ضمن السلطة المقررة له.

### القواعد

1. Agent لا ينشئ Authorization لنفسه.
2. Agent لا يصبح Authority Policy.
3. Agent لا يصبح Authorization Grant.
4. Agent Action لا يصبح Grant لمجرد تسجيله.
5. Agent لا يملك Activity أو Membership أو Role Assignment لمجرد التنفيذ.
6. Agent لا يملك Financial Account أو Clinical Record.
7. Agent لا ينقل Domain Ownership.
8. Authority Policy قد تحدد حدود السلطة المقررة للوكيل.
9. Authorization قد تكون أساساً لعمل Agent عندما يكون ذلك مقرراً.
10. التفاصيل الخاصة بسلطة الوكيل تؤجل إلى SPEC-0017 وSPEC-0018 وما يرتبط بهما.
11. DEC-0006 وDEC-0007 لا تتحول هنا إلى قرارات تفصيلية.

## 27. Open Decisions / Dependencies

### DEC-0001 — Jurisdiction / Market

**مفتوح.**

قد تختلف قواعد السلطة والخصوصية والملكية والعمر والعمل والوصول باختلاف الولاية أو السوق.

- قاعدة أبوية عامة.
- سن قانوني عام.
- حق مالك النشاط في كل البيانات.
- قاعدة قانونية للملكية.
- قاعدة صحية أو تعليمية عالمية.

### DEC-0004 — Family / Delegation

**مفتوح.**

لا تفترض المواصفة أن Family Relationship تنتج Delegation أو Authorization تلقائياً.

لا تحسم:
- متى يصبح الوالد مفوضاً.
- مدى التفويض الأسري.
- قواعد عمر الطفل.
- قواعد الولاية الأبوية.
- حدود البيانات الأسرية.

### Q-0027 — قيود الصلاحية

يبقى سؤال التفاصيل المتعلقة بتقييد أفعال الأدوار والوصول إلى بيانات الأفراد مفتوحاً حيث لم يُحسم.

### Q-0002

يبقى سؤال حدود الخصوصية والسياق مفتوحاً ضمن ما ورد في Stage 3.

### DEC-0006 / DEC-0007 — Agent

تبقى حدود أفعال الوكيل التفصيلية ضمن المواصفات المخصصة للوكلاء، ولا تُحسم هنا.

### DEC-0013 — Offline / Lost Device

قد تؤثر في الحالة التشغيلية والوصول والعمليات المعلقة، دون جعل الحالة المحلية Authorization نهائية.
